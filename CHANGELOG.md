# Changelog

All notable changes to this repository are recorded here. One version covers the repository
(`sdc-tools`, `sdc-watch`, `sdc-goals`, `runbook`, `ui/`, the plugin manifests), released under bare-version
tags such as `0.1.0`. The crates are `publish = false`; releases are source releases at
bare-version tags (`docs/releasing.md`).

## [Unreleased]

### Fixed
- The cycles suite (`task test:cycles-loom`) builds nothing. Every cycle that reached `tests.run` or a bug-fix check ended `ProgramError ... exit status 127`: Loom gives a bound program `PATH` and `LOOM_*` only, the `slot` an agent's PATH now finds first reads `HOME` to find the pool, and a cycle's work directory under `$XDG_RUNTIME_DIR` is one the build node does not sync. The `slot` first on the PATH of the suite's programs is now `sdc-recorded-pool` (`driver/src/bin/sdc-recorded-pool.rs`), which answers each build and test command from a recording in `cycles/recorded/`, keyed by the sha256 of the command and of the tree it runs in; a command with no recording is a program error whose line names the digest, and the slow lane `task test:cycles-record` records it through the pool from a copy of the tree under `target/` (`docs/cycles-suite.md`, "Recorded build and test results"; tests in `driver/tests/recorded_pool.rs`). `runbook doctor` names `sdc-recorded-pool` as an optional helper (`runbook/src/doctor.rs`).
- A bug-fix check whose pool job exits 127 or 126 (the command was not found or could not run) is a program error of the step, exit 127 or 126 with a line that names the command, and no verdict: `repro-run` read it as `not red`, so the case ended `not_reproduced` (`driver/tests/bugfix_languages.rs`).
- The forge's log of `task test:runbook` shows the runner's output again: the nextest output, the ten slowest and the budget line. The steps that print a runner's output opened the output again with `exec` and redirections only, and go-task 3.52, the release the forge installs, closes the file that form opens at the end of its line, so every line after it was lost. They open it for a group now (`{ ...; } >> /dev/stdout 2>> /dev/stderr`), which keeps every line on the forge and under `task check` where node makes the shared output non-blocking. The build and clippy of the four crates and the tests of watch and goals are the tasks `check:crates:lint` and `check:crates:test` of `check:steps`; `task check:task-output` (part of `task check`, no network) fails on the `exec` form and runs the driver, runbook and UI steps with stand-ins beside a node process under the local go-task; `task check:task-output:forge`, the lane to run when a shell block of the Taskfile changes, runs them and the two crate tasks the forge's way with the forge's go-task (fetched once, its sha256 checked); both fail on a lost line.
- `sdc-conform-adapter` holds the port it tells a product until the product ends (a socket bound with `SO_REUSEADDR` that never listens), so the kernel gives it to no other process that asks for a port. It freed the port and handed the number on: another server could take it first, and the product failed with `AddrInUse` or the other server answered `start.ready` in its place (about one of two runs of the driver's 58 conformance cases on a loaded build node). A product that cannot bind a held port (its log says "address already in use") is started once more on a port that is not held, logged `port_not_held` (`docs/conformance.md`, "The adapter").

## [0.10.0] - 2026-11-24

Two entries are marked breaking: the daemon has no built-in confinement, and `runbook run` has no money limit built in.
A `runbook.toml` supplies the defaults of `runbook run` and names the directories runbooks are loaded from. A daemon run
is never unbound, takes an autonomy level and a decider, records the step in flight and takes its runbook at submit,
and the daemon drains on SIGTERM or SIGINT. A binding names the per-call budget of its programs. The Products tab lists
what the run wrote. `runbook run` and its watcher write and read the files of a run directory without following a link (see
Fixed). `task check` ends within its 120 s, and the
test step of `runbook/` fits its budget on the forge. No evaluation run was made on this code. The longer note is
`docs/releases/0.10.0.md`.

- A `runbooks = ["dir", ...]` list in `runbook.toml` names the directories runbooks are loaded from (story `runbooks-load-from-configured-paths`). `runbook list`, `run`, `serve`, `check` and `doctor --for` resolve a name through one function (`runbook::runbooks::load`) over those directories in order and the built-in set last; `list` prints name, kind, version, directory and title. - A daemon run is never unbound. `runbook serve --runtime loom` requires `--max-wall-seconds`, `--max-llm-calls` and `--cap-micro-usd` (no default; a daemon started without one refuses to start, exit 1, and names each missing option) and takes a ceiling for each (`--max-wall-seconds-ceiling`, `--max-llm-calls-ceiling`, `--cap-micro-usd-ceiling`, default the cap). A run at a cap ends as `runbook run` does (`stopped: wall time`, `stopped: llm calls`, `stopped: spend cap`), with the event `runbook.cap-reached`, and a wall cap ends a sleeping step and a wait on a decision. The spend cap is the run's own: it is the most one run spends, and the spend of other runs of the runbook never reduces it. Spend is booked in a ledger per runbook under the state directory (`ledgers/<runbook>.json`, each entry and reservation keyed by the run), through the module of `runbook run`, which moved into the library crate with the cost reader and the call-budget reader (`runbook run` keeps its shared ledger and its meaning). A program that names a per-call budget (`--max-budget-usd <v>` or `--max-budget-usd=<v>` in its own arguments, from the bindings the run reads; the larger when named twice) reserves that budget as it starts, against what the run has left, and is not started when the reservation is short. A program that names none may call a model all the same and reserves the largest budget its runbook's bindings name (root and children), so a step near the cap whose program makes no model call may be stopped; a runbook with such a program and no budget in any binding is refused at submit naming the reason, and so is a budget that is no number of USD of 0 or more, naming the action. A reservation of a run that no longer lives counts against no run, and a reservation id does not repeat within a ledger. A cap of another JSON type than a string in `settings`, an out-of-range number such as `1e999` included, is refused naming the cap, over HTTP and through `submit_run`, and the tool description says the caps are strings. `read_run` shows each cap and what is used (`used_wall_seconds`, `used_llm_calls`, `spent_micro_usd`) in `settings`. `docs/daemon-api.md` ("Caps of a run") and `docs/engine.md` say it; the cases hold it (`runbook/tests/daemon/caps.rs`, each under 5 s, no model call).
- A binding names the per-call budget of its programs without the argv, so a runbook whose programs call no model is no longer refused at submit and nothing is passed to a tool that does not take `--max-budget-usd`. The member `max_budget_usd: <number>` of a program action (an action with `executor.argv` or `arguments_from`) is the budget that action's programs reserve, `0` for a program that calls no model; the same member at the top of a bindings file covers every program action of that file that names none itself and not a child file an `open` action names. The order is `--max-budget-usd` in the argv, the action's member, the file's member, the largest budget of the runbook (argv values and members). A runbook whose every program has a budget from one of these needs no budget elsewhere; one with a program that has none and no budget anywhere is refused as before. Refused at submit (daemon) and at load (`runbook run`), naming the action or the file: a member that is no YAML number of 0 or more, an action whose argv and member name two budgets, a member on an action that runs no program; `runbook check` names the same. The member is never passed to the program: Loom refuses a member it does not know, so a run's copy of the bindings holds none and keeps the members beside it (`bindings/.call-budgets.json`, inside the copy's digest), and `runbook run` reads them where it reserves; it lowers only argv values to what its cap has left, a member is reserved as written. `docs/loom-bindings.md` ("The per-call budget of a program"), `docs/daemon-api.md`, `docs/engine.md` and `docs/loom-run.md` say it; cases in `runbook/tests/daemon/caps.rs`, `runbook/tests/loom_run/model_call.rs`, `runbook/src/budget.rs` and `runbook/src/check.rs` hold it (each under 1 s, no model call).
- `runbook serve` drains on SIGTERM or SIGINT instead of ending the runs it holds: it refuses a submit (`503`, `{"refused": "draining", "live_runs": <n>}`; the MCP tool `submit_run` gives the same body), serves reads, streams, answers and cancels, lets every live run go on to its own outcome, journals `daemon.draining` (with the live run ids) and `daemon.drained`, and exits 0 when no run is live. Every answer carries `X-Runbook-Draining: <n>` while it drains, the `401` and `403` of the guard included (the specification's rows have no member for it). A second signal, or `--drain-seconds <n>` (any number up to 18446744073709551615, default no bound; a value too large to be a point in time is no bound), ends it at once, with exit 75 when a run was live and 0 when none was left (`docs/cli.md`, `docs/daemon-api.md`): each live run ends `orphaned` at that moment with a `runbook.run-orphaned` event whose reason says the daemon was stopped while the run was live, not that it started again. `docs/daemon-api.md` ("Stopping the daemon") says how a person or a task stops the daemon so that no run is lost, and the systemd unit it needs (`KillMode=mixed`, `TimeoutStopSec=infinity`). The cases in `runbook/tests/daemon/drain.rs` start the daemon as a process over the engine fixture runbook, and one calls the stop guard of `serve` with a future that panics.

Each answer names who gave it: `rule:<name>` or `decider:<kind>`, never a person, and a client's `answered_by` is trimmed of ASCII whitespace and refused when it holds a non-ASCII or a control character or starts, in any case, with `rule:`, `decider:` or `router:` (the refusal prints no byte of it). At `A5` the decider is not asked about a close of a case that one outcome of the same wait already closed (the request is not raised, as `runbook run` does not ask it). A model decider of the daemon is given a link in the run's private directory below `$XDG_RUNTIME_DIR/runbook`, never the login file's own path, and the link goes when the run ends; a run of kind `model` with a login file and no `XDG_RUNTIME_DIR` does not start. `docs/engine.md` "Autonomy and a decider", `docs/loom-run-settings.md`, `docs/mcp.md`.
- A run of the daemon on the engine (`--runtime loom`) records the step in flight. Before each bound program starts (the program of an action, or the `handoff_when` check of one) the daemon records the run event `runbook.action-started` (record: `case`, `action`, `role` of `program` or `check`, `try`; a member that is not known is absent), and while the program runs the view `run` (`GET /daemon/views/run`, MCP `read_run`) has `step_in_flight`: `action`, `case_id`, `started_at` and `seconds`. ### Changed

- Breaking: the daemon has no built-in confinement (story `daemon-default-confinement-is-stated`). A client that submits without `confinement` to a daemon that states no default (no `--default-confinement`, no `confinement` in the `runbook.toml` it reads) is refused `400` by name and nothing is written; before, such a submit ran at `linux`. The remedy is one line: start the daemon with `--default-confinement linux` (or `local`), or name `confinement` in the submit.
- The Products tab lists what the run wrote, not every file under `work/`: the files its records name as written or changed by an action, grouped by the step that wrote them, newest step first. What the run was seeded with is one closed line, "Inputs", with the trees and their file counts, and a seeded file an action changed or added is a product marked `changed`, `added` or `removed`. The tab opens the last file the last finished step wrote, never an input. The list is not cut by depth: a bound of 500 lines says how many are not shown. A run without `seeded.json` (an older run) shows today's listing and says why (`ui/README.md`). The answer is bounded and says what it left out: an action name is cut at 256 characters and counted (`cutStrings`), a path of a record over 1024 characters is not listed and is counted, the server keeps at most 100 000 records of `fs/changes.jsonl` for one run and keeps the state of the records with them (an answer for a run that did not change reads no record again), a reader that stops before the end of that file (a line over 32 MiB, bytes with no line end in a whole chunk, the record bound) is said in `recordsStopped` with `truncated`, and a file it cannot take one record from is answered as the listing with the reason. A name behind a link that leaves the run is counted as left out whether or not anything lies behind it: nothing outside the run is looked at before the run-path check has decided.
- The live feed, the File changes tab and the route of one change say when the list of file changes the server keeps for a run is not the whole record: `/api/live` carries the same `recordsStopped` as `/api/products` in `fs`, both pages show it as a note, the File changes tab also when the list holds no record, and `/api/fschange` answers a change after the last record the list holds as 404 "past the bound" with `recordsStopped`, never as "no such change".
- What the server keeps of `fs/changes.jsonl` for one run is bounded in bytes as well as in records: at most 64 MiB of record lines without the diff, a late attribution line that replaces one already kept counting what it adds to the longest line counted for that change (`SDC_UI_MAX_RECORD_BYTES` names it for a test), and the answer says `recordsStopped` with the cause `bytes` when that bound stopped the reader.
- A value of `SDC_UI_MAX_RECORDS` or `SDC_UI_MAX_RECORD_BYTES` that is not a whole number of at least 1 that a number holds exactly (zero, negative, a fraction, text, empty, or one past 2^53 - 1 such as `1e300`) is the default bound; a fraction no longer makes a bound that keeps no record, and a huge number no longer turns the bound off.
- An action name is cut at 256 characters and a path of a record is refused over 1024 characters, counted as characters: a character of more than 16 bits counts one and the cut never falls inside one (it counted 16-bit units, so a name of such characters was cut to half the documented length).
- One answer of `/api/products` resolves at most 8 link components of one name (`maxLinks`); a name past it is left out as a name behind a link that leaves the run is, and is counted in `linkCut` besides `leftOut` (`cut: "links"`), with a note on the tab, and `linksResolved` counts the link components the answer resolved over the names it lists (at most 500; at most 8 per name), so a record file of names with hundreds of links no longer holds the inspector for seconds.
- `runbook run` writes `seeded.json` and `seeded-files.jsonl` into the run directory right after the seed ends: the top-level entries of `work/` with their kind and file count, and every seeded regular file with the SHA-256 of its content (the form of `after` in `fs/changes.jsonl`). The records cannot tell a seeded file from a file the first step wrote (the watcher starts before `work/` exists), and this record is the mark. Links are not followed, dot entries are skipped, the listing stops at 20 000 files and says `complete: false`, as it does for a directory or file it cannot read, a name that is not UTF-8 text and a walk of more than 200 000 entries (`docs/loom-run-directory.md` names the five causes), and the record holds no absolute path, no environment and no file content (`docs/loom-run-directory.md`, `docs/fs-changes.md`). The temporary file of each of the two records is created new, after what lies at its name was removed, so a link at that name is never written through.
- Breaking: `runbook run` has no money limit built in (the operator: "runbook should not have any limitations in terms of money cap - there is basically no technical limitation at all"). `--spend-ledger`, `--cap-micro-usd` and `--max-llm-calls` are each optional, alone and together, for every run, under `--confinement local` and `substrate`, with or without a model node, with `--dry` and in the library; a run that names none opens no ledger, refuses nothing and applies no limit. A named cap stops the run when reached, as before (exit 4 for the spend cap, exit 6 for the call cap), and a named 0 means spend nothing: the run starts and a model program that may spend is stopped before its first call. `--cap-micro-usd` without `--spend-ledger` is counted in the run itself, no file is written; `--spend-ledger` without a cap records and stops nothing. Gone, and a script that read them reads nothing now: the usage error (exit 64) for a missing `--cap-micro-usd`, `--max-llm-calls` or `--spend-ledger` of a run with a model node, the refusal by name of a run without a model node under `--confinement local` without caps (exit 2, `NO_NETWORK_LEVELS`), and `stopped: model call` (exit 13, cause `model_call_without_model_node`, the event `cap_reached` with cap `model_node`) with the checks that ended a run by it (the bindings copy read again, the tree manifest, a recorded call, the model decider, `--conformance observe`). In a run opened without a model node, with a spend cap or a call cap named, the printed command of a handoff still takes one step and the caps are read between two steps; with none named it runs as printed, and in a run opened with a model node it runs as printed under a named cap too (the bound for it is the story `handoff-under-a-named-cap-runs-one-step-at-a-time`). A call of unknown cost in a run that names no spend cap books nothing and is recorded with `cost_unknown` true and `cost_usd` null. A settings member `cap_micro_usd` or `max_llm_calls` without its option names the cap, and beside its option must still equal it. The decider has no built-in limits: a decider that names no `decider.max_calls` or `decider.max_budget_usd` is not limited (the old defaults were 20 calls and 0.25 USD per call); a named one holds as before. `--max-wall-seconds` stays required and unchanged. `docs/loom-run.md`, "The money options".
- A money cap is optional in the experiment records, replay and the node programs of `driver/` (story `caps-are-optional`): none named means no limit and no refusal, one that is named stops as before. `sdc-experiment` takes a record that names no `loom.cap_micro_usd` and no `max_llm_calls` (also in the old driver's launch settings) and no `free.max_usd`; the command of a run then carries no `--cap-micro-usd`, no `--max-llm-calls`, no `--spend-ledger` and no `--max-usd`, and a named value is held to a whole number where 0 spends nothing (`free.max_usd`: a finite number of at least 0;
