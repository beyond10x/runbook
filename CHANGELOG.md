# Changelog

All notable changes to this repository are recorded here. One version covers the repository
(`sdc-tools`, `sdc-watch`, `sdc-goals`, `runbook`, `ui/`, the plugin manifests), released under bare-version
tags such as `0.1.0`. The crates are `publish = false`; releases are source releases at
bare-version tags (`docs/releasing.md`).

## [Unreleased]

### Added
- `runbook.toml` names the daemon's context roots: `context_roots = ["<dir>", ...]`, at most 64, a relative path taken against the file's directory and `~` not expanded (story `context-roots-are-keys-of-runbook-toml`; `docs/daemon-api.md`, "Context roots"). `--context-root` of `runbook serve` adds to the file's list; each root is canonicalized once. `runbook serve` names each root with its source on standard error when it starts, `runbook config` prints the file's list with its origin, and a file that a program of a run finds by the walk has no such key.
- A submit and a delegation take `workspace_exclude`, names or relative paths the copy of their context leaves out besides the daemon's list (story `the-context-copy-skips-git-and-excluded-paths`; `docs/daemon-api.md`, "The copy of a context"). At most 64 entries; one that is empty, absolute, holds an empty, `.` or `..` part or a NUL, or is longer than 200 characters, is refused `400` by the member and the entry's place. A run adds entries and removes none of the daemon's; `runbook.submitted` records them.
- A delegation can change a repository on its own branch, first slice (story `a-delegation-changes-a-repository-on-its-own-branch`; `docs/daemon-api.md`, "A delegation that changes a repository"; `docs/model-routes.md`, section 7). The operator lists the repositories in `runbook.toml` (`[repositories.<name>]`: `path`, `base`, `remote`, `default_branch`, `commit_name`, `commit_email`, optional `push_token_file` and `deny_paths`; none by default). `delegate` and `runbook delegate` take `repository`, the name of an entry, never a path; the daemon refuses with `422 repository-refused` (`sdc.daemon.RepositoryRefused`) a name that is not an entry, a protocol other than `delegation-change` beside it, a default level other than `local`, a runtime without the daemon's agent node, and a base that names no commit. The run takes the path `change` and the runbook `delegation-change`: when it starts the daemon makes the run's worktree with the host's `worktree` command at the base resolved at the submit, and the one agent node (`sdc-node delegation.change`) works in it. When the outcome is `delivered`, the daemon commits the change under the entry's identity on the base and pushes it as the new ref `refs/heads/runbook/<run-id>`: never forced, never over a branch of that name, never with a path of `deny_paths` (by default `.github/`, `.gitlab-ci.yml`, `.gitmodules`) or a link out of the worktree, never when the worktree's `.git` file changed, never after a cancel; every git call runs without the operator's configuration, hooks and credential helpers and is killed after 120 s, the push runs from a bare repository of the daemon's own so the checkout's configuration does not steer it, and the push token reaches git only through the `runbook` binary as git's askpass, for the remote's host only. The run events `runbook.pushing` (written right before the push), `runbook.handed-back` (branch, commit) and `runbook.hand-back-refused` (reason) record it, and the view `delegation-result` gains `repository`, `branch`, `commit` and `handback_refused`. A run that ends any other way pushes nothing and keeps its worktree. Not in this slice: the draft merge request, a forge client, the level `linux`, a base named by the delegation. The specification's `Delegate`, `Delegation`, `DelegationResult` and `DelegationPath` gain the members; schema, OpenAPI and both conformance suites are regenerated. Tests: the cases of `runbook/tests/daemon/delegate_change.rs` and `runbook/tests/daemon/adversary_delegate_change.rs`, `handback::tests` and `the_agent_node_of_a_change_delegation_works_in_the_worktree_and_its_prompt_is_its_golden` (`driver/tests/sdc_node.rs`).

### Changed
- A context root of `runbook serve` (of the file or of `--context-root`) that does not exist is created with mode 0700, its missing parents too, where it stopped the start before (story `context-roots-are-keys-of-runbook-toml`). An existing root is never changed: one with a group or other write bit now stops the start naming its mode, one wider than 0700 without them is named in the start log. A root that is no directory, or that cannot be read or created, stops the start naming the key or the option and the path, exit 2 (was exit 1, `state directory: context root ...`). The roots are made ready after the principal, the token and the listen address are checked and before the state directory is opened. `Daemon::start` of the library still refuses a missing root.
- Breaking: the copy of a run's context into its workspace (`context_path` of a submit, `workspace` of a delegation) leaves out every entry named `.git`, a directory or a file, and the exclude list `[delegation] copy_exclude` of `runbook.toml` (default `target/` and `node_modules/`; a name matched at any depth, or a relative path from the context root), and is bounded by `copy_max_entries` (default 50,000) and `copy_max_bytes` (default 256 MiB) (story `the-context-copy-skips-git-and-excluded-paths`; `docs/daemon-api.md`, "The copy of a context"; `runbook/src/context_copy.rs`). It copied the tree whole before, symbolic links left out as now. A context over a bound fails the run's start `context-over-bound: ...` naming the bound, and nothing of it is copied. Each copy records the run event `runbook.context-copied` with the list it applied, the entries and bytes it copied and the count of entries it skipped.
- A call of `b10x-loom` (`runbook run --loom`) ends when the child exits, not at the next look of a 10 ms poll: the exit is waited for on a thread of its own, and the cancel and the wall-time deadline are still looked at every 10 ms (`runbook/src/loom_run/child.rs`). A run of the daemon's engine ends when its steps are done, not at the next 20 ms look of its watcher (`runbook/src/engine/mod.rs`). The test step `task test:runbook` (story `the-runbook-test-step-stays-under-its-budget`): the fake `b10x-loom` of the `loom_run` tests starts one shell per call instead of three (an answer is a `printf` it sources; a call's environment is recorded only for a test that reads it, and `Call::env` refuses to answer without it), and three cases that waited out fixed times wait for the event instead or run their two sub-cases at once. The summed test time fell from 295 s to 267 s at a load average of about 21 (the step 60.1 s to 54.6 s), the `loom_run` tests from 125 s to 79 s.
- The aep pin is aep 0.81.0 (`driver/aep-pin.json`, tag `0.81.0`, commit `ff194ee2`; replaces 0.80.0), the first aep release with static Linux archives: the pin names `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` beside the four gnu and darwin archives, each with its archive and binary digests. So the `sdc-conform aep-install` of a musl build (the musl release archive, given a checkout's pin) installs the musl aep, which needs no glibc, where it installed the gnu aep (`conformance::platform_for`; `driver/tests/aep_pin.rs`, `a_musl_build_takes_the_pinned_musl_aep`). The gnu aep of 0.81.0 needs glibc 2.39 or newer. Between 0.80.0 and 0.81.0 aep changed no verb, flag or store version that Runbook calls. The ess pin (ess 0.98.0) still names no musl archive: a musl `sdc-conform ess-install` installs the gnu ess (`docs/releasing.md`, "The archives").
- The agent node of a delegation gets no more turns than its run has model calls left (story `the-free-runs-turns-follow-the-runs-call-cap`; `docs/daemon-api.md`, "A delegation"). The free run's bindings start `sdc-node delegation.free` with `--max-turns 40`, and a daemon run whose `max_llm_calls` was below 40 let the agent run on until the relay refused its calls `429 cap-reached`, so the run ended on the cap with no result. As the agent node of a delegation starts (the free run's, each action of a generated protocol, `delegation.change`), the daemon now names in `RUNBOOK_CALLS_LEFT` the run's call cap (the delegation's `settings.max_llm_calls`, else the daemon's `--max-llm-calls`) less the calls the run has used, classify and build included, at least 1; `sdc-node` takes the smaller of that and its `--max-turns`, and the call's `request.json` names the bound. A cap of 30 gives 30 turns, 50 gives 40, and a classified delegation with a cap of 5 that spent 2 calls on classify and build gives 3. Without the variable the binding's bound stands; `sdc-node` refuses a value that is not digits for a whole number of at least 1 before it calls a model (exit 64). A call the CLI sends again after a failed answer, or a compaction, is counted by the relay and is no turn, so such a node can still reach the cap; and a node that spends every call left still ends the run `stopped: llm calls`, as before. A cap of 0 is refused at submit as before. The bound nodes of the SDC runbooks keep their fixed `--max-turns`.
- `task test:driver` runs the static musl aep on every Linux host, so a host with glibc older than 2.39 runs the driver tests (story `the-driver-tests-install-the-musl-aep`; `docs/forge-gate.md`). The step took the aep of its tests from a gnu `sdc-conform`, which names the pin's gnu aep, and the gnu aep of 0.81.0 does not start below glibc 2.39. It now runs `sdc-conform` built for `<arch>-unknown-linux-musl` (`cargo run --target`) and puts `<cache>/<version>/<arch>-unknown-linux-musl/` first on the tests' `PATH`; it does not look at the glibc version. The rustup target and the aep come from the task `deps:driver-aep`, which `test:driver` depends on and which is its only network step: it adds the target when missing and installs the pinned aep with the musl `sdc-conform` when `aep-path` finds none, and makes no request when both are present; `test:driver` and its tests make no network request and stop with the install command when the aep is missing. The driver crate has no C code, so no `musl-tools`. The case `aep_pin::the_aep_the_driver_tests_run_is_static` fails when the first `aep` on that `PATH` asks for a dynamic loader (`PT_INTERP`). On other systems the step builds `sdc-conform` for the host as before. Since a gate installs, `sdc-conform aep-install` and `ess-install` may run at once into one cache (the steps of two checkouts): each downloads and unpacks under names of its own process and renames the checked file into place, where 3 of 4 concurrent installs failed on the shared `unpack/` directory (`aep_pin::installs_into_one_cache_at_the_same_time_all_succeed`).
- A wake of a managed route books against the route's daily cap only when the gateway took it, a `2xx` answer (story `a-wake-is-booked-only-when-it-succeeds`; `docs/daemon-api.md`, "The wake of a managed route"; `docs/model-routes.md` section 3 point 4). A wake answered `4xx`, `5xx` (`target-unavailable` when the pod's start failed, `spend-ceiling`) or not answered within 5 s booked its `wake_cost_micro_usd` all the same, so three failed pod starts could use up a day's cap with no pod started and the runs after them waited 900 s for nothing. Such a wake now books nothing, the run's `runbook.route-wake-answered` naming the gateway's code; a wake not answered yet still counts, so two runs cannot both pass the cap, and a run joins only a wake that may still start the model. The answer to a wake whose run was cancelled while it was out is the daemon's journal line `route.wake-answered` and books the same way (a 202 is booked, a 503 is not); a wake out when the daemon was killed stays booked after the restart. A runbook older than this one refuses to replay a journal that holds a `route.wake-answered` line. A `5xx` other than `spend-ceiling`, or no answer, is sent again after 30 s of the daemon's clock while the gateway gives the model as `stopped`, within the run's wait for its route and never past it, each try one more `runbook.route-wake` and `runbook.route-wake-answered`.
- **Breaking** for a managed route that declares the new key `price_per_hour_micro_usd`: its daily cap `wake_daily_cap_micro_usd` counts the pod's measured time beside its wakes, so the same cap admits fewer wakes (story `a-managed-route-books-its-pods-measured-time`, the operator's pick A of 2026-11-27, which replaces "Runbook books wakes only" of `docs/model-routes.md` D-3; section 5; `docs/daemon-api.md`, "The pod's time of a managed route"). A route without the key books as before. A run uses the pod from its start to its end, or to the first read of the pod as not ready: while a started run takes such a route the daemon reads its status every 5 s of its clock, each change a run event `runbook.route-pod-phase`. The pod's time is split equally over the runs that used it in each stretch (a millisecond that does not split goes to the first submitted; `runbook/src/pod_time.rs`), and just before a run ends its share is the run event `runbook.route-pod-time` (`pod_millis`, `share_millis`, `price_per_hour_micro_usd`, `cost_micro_usd`): two runs that share 30 minutes at 3.00 USD per hour book 0.75 USD each. A run the daemon ends `orphaned` books up to that mark; a failed status read changes nothing. A wake's `runbook.route-wake` on such a route holds `pod_micro_usd`, and a wake the rest of the day's cap of wakes and pod time does not cover is not sent (`wake cap reached`). The price is the route's own: the gateway serves its `price_per_hour_usd` on no route a client reads.
- The UI test step costs less wall time (story `the-ui-test-step-stays-under-its-budget`): the cases that prove what the page does over a stretch of time (how often it asks a daemon that refuses it, that it sends an answer not again by itself, that it reads a tree again while the daemon answers 503, that the copy word goes back) spend the page's own time through Playwright's clock (`ui/test/page-time.mjs`: steps of 50 ms, each ended when every request the page made has ended) where they waited 2 s to 5 s on the host's clock; the page keeps its real navigation entry under that clock, which tells it that the daemon served it. The start-form cases hold a stand-in's answer until the event they wait for has happened (a promise the test resolves) where they held it 0.8 s to 1.5 s and then waited up to 2.2 s more; the dropped-page case runs its server's rounds every 100 ms; the fourteen servers of the environment-bound case of the change-record reader start at once; the Products redraw case moves the page's clock past its 1.5 s wait. The step keeps four workers. Measured on the workstation: the slowest test 5.5 s before, 3.6 s after; the step alone 69.2 s to 74.9 s before, 64.2 s to 70.5 s after; inside `task check` the step ran out of its 120 s with about 190 tests not run before, and ran all 684 in 114.2 s before the 503 and copy-word cases were changed.

### Fixed
- The two race specs of the inspector's file reader (`ui/test/security-products-race.spec.mjs`, `ui/test/security-products-2-race.spec.mjs`) no longer need `mv --exchange`, which GNU coreutils has only from 9.5 on (story `the-race-specs-swap-without-mv-exchange`). On a host with an older `mv` the flag was refused in every turn of the child's loop, no swap happened and each case ran to its 30 s timeout. The child is now the test helper `ui/test/exchange.rs`, which exchanges the two names with `renameat2` and `RENAME_EXCHANGE`; `ui/test/exchange.mjs` builds it with `rustc` once per digest of its source into `ui/target/exchange/`. Each case exchanges twice at its start, so a missing `rustc`, a failed build or a kernel or file system that cannot exchange fails it at once with one line naming that; an exchange loop that ends fails the race at once, and the race also ends after 20,000 reads in which a state was not seen 100 times. The reader's code is unchanged.

## [0.14.0] - 2026-11-27

One entry is marked breaking: a daemon run takes a model route, named or `[route_policy] default`, only when it has a
model step, so a run whose programs all name the budget 0 takes no route and wakes nothing. A release tag builds two
archives of an installed prefix, gnu and static musl, and `runbook` links Loom 0.63.0. A failed model call booked after
its step ended no longer fails a run, a caller that hangs up ends its call at the gateway, a case of a run ended at a
cap shows the cap and not `Stuck`, and the bindings checks leave out route files. No evaluation run was made on this
code. The longer note is `docs/releases/0.14.0.md`.

### Added
- Release archives (story `static-musl-release`; `docs/releasing.md`, "The archives"; `README.md`, "Try it"). A tag push runs `.github/workflows/release.yml`: it refuses a tag that is not the version of `runbook/Cargo.toml`, packs the prefix `scripts/install.sh` lays out as `runbook-<version>-x86_64-unknown-linux-gnu.tar.gz` and, static, `runbook-<version>-x86_64-unknown-linux-musl.tar.gz`, each with a `.sha256` file, and uploads them to the tag's Release. The musl job fails unless `file` and `ldd` call every program static and each answers `--version` with exit 0, its name and the release version in a plain `alpine` container; a pull request that changes the workflow, a `Cargo.toml`, a `Cargo.lock` or `rust-toolchain.toml` runs that job without upload. The listings the checks read (`nm`, `tar -t`) go to a file first, never through a pipe into `grep -q` or `head`, which under `pipefail` can fail a check that held; `install::release_workflow` refuses such a reader in the workflow. The musl `runbook` allocates through mimalloc (cargo feature `mimalloc`, on by default, compiled only for a `musl` target; the gnu build links none). Every helper program answers `--version` with its name and the version (`sdc_tools::answer_version`; `sdc-watch` through clap), held by `install::every_program_answers`, and `sdc-conform` on a musl build takes a pin's `<arch>-unknown-linux-musl` archive when the pin names one and `-linux-gnu` otherwise (`conformance::target_triple`, `platform_for`; the pins of aep and ess are unchanged): both were in the code of 0.13.0 without an entry. The musl build needs Loom 0.63.0 (below).

### Changed
- Breaking: a daemon run takes a model route, named or `[route_policy] default`, only when it has a model step (story `the-default-route-wakes-for-runs-without-a-model-call`; `docs/model-routes.md`, section 2; `docs/daemon-api.md`, "The route of a run"): its decider is `model` above `A0`, or a program the run's runner starts for its runbook (an `executor.argv`, an `arguments_from` or a `handoff_when` check) is an agent node or reserves a per-call budget above 0 (its `--max-budget-usd`, else `max_budget_usd` of its action, else of its file, else the largest of the runbook); bindings that cannot be read, a child file among them, count as a model step. A run whose programs all name the budget 0 took the default before and, on a stopped managed route with `wake_on_submit`, sent and booked a wake and waited for the model; it now takes no route, wakes nothing and runs at once, and its programs get no route file. A submit of such a run that names a route (`model_route`, `model_routes`) is admitted as before but takes no route either, where it took the named route before; its first event `runbook.submitted` names the routes asked for under `model_route_not_taken` with the `reason` "the run makes no model call". A run whose runbook runs no program at all is still refused `422 route-refused` when it names a route.
- The crate `runbook` links Loom 0.63.0 (`b0a0dfda31f722d5b38208f6fb9d90edacd7165b`, tag `0.63.0`; replaces `112a97e1`, Loom 0.62.1) for every Loom crate, one git rev (`docs/library-entries.md`, row R). Loom 0.63.0 moves Substrate from 0.24.0 to 0.29.0, whose host builds for `x86_64-unknown-linux-musl` (`b10x-substrate-host` 0.24.0 called `nix::fcntl::renameat2`, which nix defines for glibc only), and adds `exec_subpaths` and `exec_denied_paths` to Substrate's `AppliedConfinement`; `runbook` builds and matches no such record, so no code changes with it.
- The daemon's run page counts the steps that are over apart: `4 done, 2 exited non-zero, 1 ended with no exit`, where it said `6 steps done` and `2 ended with an exit other than 0` beside it, which counted a step with an exit other than 0 twice (story `run-page-watches-a-live-run`; `ui/README.md`). The line of what runs now (`Between steps: ...`, `Cancelled: ...`) and the phone's bar use the same words; the bar shows them whole on hover (`ui/web/runsteps.js`).
- The root case card of the daemon's run page names the run by the last 8 characters of its id on one line, where the whole id wrapped over three lines at laptop width; the whole id is the label's title and a copy control's (`Copy`, accessible name "Copy run id", reached with Tab), which writes the run's id to the clipboard and says what came of it, `Copied` or `Copy failed`, in its words and in a status line for 2 s (story `run-page-watches-a-live-run`; `ui/web/app.js`, `ui/README.md`).

### Fixed
- A failed model call that the relay books after its step ended no longer fails the run (story `a-call-booked-after-its-step-ended-does-not-fail-the-run`, a regression of `a-recovered-call-does-not-fail-the-run`; `docs/engine.md`, "A gateway"). Such a call was taken with the failed calls of the step that ran next, and the run's end asked which step had failed with `refusal::failed_step`, which reads the last step of every case's log: a step of another case that had exited non-zero and gone on was found, the late call of that step became the run's cause, and the run ended `runtime-failure` right after an event that said its step went on. The booking now keeps a failed call whose step is no longer in flight apart from the step's own calls and names it under its own step with one event `runbook.model-calls-failed` when the run's calls are next recorded; it never fails the run, a refusal of the route or the gateway's spend ceiling included. A call keeps the count of step starts it was admitted in, so a call left by an earlier start of the same action is late too. Which step failed is read from the log of the step's own case only. A step whose program exits with a status its bindings take as a result (not one their `exits.error` lists) fails nothing by itself: its failed calls are named and the protocol goes on, unless the tree has nothing it can do after it. A failed call booked while its step runs settles as before. Tests: the three cases of `runbook/tests/daemon/adversary_late_call.rs`, `a_failed_call_of_a_step_whose_exit_the_bindings_take_as_a_result_does_not_fail_the_run` (`runbook/tests/daemon/recovered_call.rs`) and `a_call_of_an_earlier_start_of_the_same_action_is_late_and_a_late_refusal_of_the_route_fails_no_step` (`runbook/src/engine/gate.rs`).
- A caller that hangs up on a model call (its own timeout killed it, its run was cancelled) now ends the call at the gateway (same story; `docs/engine.md`, "A gateway"; `docs/daemon-api.md`, the relay). The relay went on reading the gateway's answer for a caller that was gone, so a managed route kept generating for minutes after the client's timeout and slowed the next run. It now closes its request to the gateway within a second, before the gateway's head or while the answer streams, and books the call once with the `cause` `call-abandoned` and the `code` `caller-hung-up`, at the tokens the answer reported so far, else at its reservation (`cost_known: false`); an abandoned call is no failed call of its step. An answer that ends within 200 ms of the hang-up is booked as answered with all its tokens: the relay's reader of a chunked answer keeps a chunk the hang-up cut into. A caller that half-closes its connection and still reads is not served: the daemon's HTTP server drops its call as one that hung up. Tests: the two `adversary_late_call_*` cases of `runbook/tests/daemon/relay.rs` that are served, `a_failed_call_booked_after_its_step_ended_does_not_fail_the_run_whose_steps_went_on` (`runbook/tests/daemon/recovered_call.rs`) and `a_call_whose_caller_hangs_up_is_closed_at_the_gateway_within_a_second_and_booked_as_abandoned` (`runbook/tests/daemon/relay.rs`); the late calls of the cases in `runbook/tests/daemon/adversary_w4.rs` stay open in a process of their client instead of being hung up on.
- The cases that refuse an unexpected program below a run no longer fail when their sample meets a child between its fork and its `exec` (story `inproc-process-sample-judges-a-child-after-its-exec`; `docs/forge-gate.md`). Such a child carries the name of the thread that forked it, `runbook` below the runner or `run-<id>` below a daemon run, and failed `only_the_programs_of_the_runbook_run_and_never_a_loom_canon_or_driver_process` 3 and `only_the_programs_of_the_runbook_run_and_nothing_is_written_beside_the_state_directory` 1 of 50 runs each. The three copies of the sample are one helper, `runbook/tests/process_sample/mod.rs`: a child that runs its parent's executable with its parent's arguments is left to the next sample, one that shows no arguments while it runs is inside its `exec` and is read again, and every other child is judged by its name, read after its arguments. A child that runs its parent's program with arguments of its own, and a forbidden program, still fail the cases. Tests only; no product code changes.
- The view `cases` no longer shows a case of a run the daemon ended at a cap as `Stuck` (story `a-case-of-a-run-ended-by-a-cap-is-not-shown-stuck`; `docs/daemon-api.md`, "The case tree of a run"; `docs/engine.md`, "The case tree of a run"). The engine gives each `run_tree` call one step, so a run that the spend cap or the call cap ended between two steps left that step's `BudgetSpent` line as its case's last stop, and the view read it as `Stuck`. A case that had not ended when the daemon ended its run at a cap is now `SpendCapReached`, `CallCapReached` or `WallCapReached`, read from the run's outcome (`stopped: spend cap`, `stopped: llm calls`, `stopped: wall time`), whatever its last stop. A tree left with no move under no cap still shows `Stuck`; a tree left without a move by the step that reaches a cap shows the cap word (a limit: telling it from a tree with a move left needs Loom to evaluate without a step, story `a-capped-runs-stuck-tree-shows-stuck`); and a case that waits on a person while its run waits still shows `AwaitingPerson`. The specification's `CaseState` gains the three variants; schema, OpenAPI and both conformance suites are regenerated. The run page labels the three `LLM budget spent`, `LLM calls spent` (the new verdict `llm_calls_spent` of `ui/web/model.js`) and `wall time spent` (`ui/web/source.js`). The same name in two directories, a directory that is missing or holds no `protocol/` or no `bindings/`, a link that leads out of a directory and a dangling link are errors that name the directory (or both); nothing of a configured directory is executed at `list`, `check` or `doctor`. `runbook check --for <name>` checks one runbook's directory; `runbook serve` refuses a set that `list` refuses before it listens, and its engine looks a name up in the same order; a name of the built-in set is never taken from a configured directory, a name that a directory gains after the daemon started is refused at that submit by name, a configured runbook cannot turn a built-in one into a child, and the view `runbooks` lists no name that two directories hold. The list is the one value `runbook serve` takes from the file: the caps of the daemon and their ceilings come from its options alone, and a file's `cap_micro_usd`, `max_llm_calls` and `max_wall_seconds` stay the defaults of one `runbook run`. `docs/loom-run.md` "Runbook directories" has the rules.
- A daemon run is never unbound. `runbook serve --runtime loom` requires `--max-wall-seconds`, `--max-llm-calls` and `--cap-micro-usd` (no default; a daemon started without one refuses to start, exit 1, and names each missing option) and takes a ceiling for each (`--max-wall-seconds-ceiling`, `--max-llm-calls-ceiling`, `--cap-micro-usd-ceiling`, default the cap). A submit names its caps in `settings` (`max_wall_seconds`, `max_llm_calls`, `cap_micro_usd`), lower or higher up to the ceiling; one over the ceiling is refused at submit naming the cap and the ceiling. A run at a cap ends as `runbook run` does (`stopped: wall time`, `stopped: llm calls`, `stopped: spend cap`), with the event `runbook.cap-reached`, and a wall cap ends a sleeping step and a wait on a decision. The spend cap is the run's own: it is the most one run spends, and the spend of other runs of the runbook never reduces it. Spend is booked in a ledger per runbook under the state directory (`ledgers/<runbook>.json`, each entry and reservation keyed by the run), through the module of `runbook run`, which moved into the library crate with the cost reader and the call-budget reader (`runbook run` keeps its shared ledger and its meaning). A program that names a per-call budget (`--max-budget-usd <v>` or `--max-budget-usd=<v>` in its own arguments, from the bindings the run reads; the larger when named twice) reserves that budget as it starts, against what the run has left, and is not started when the reservation is short. A program that names none may call a model all the same and reserves the largest budget its runbook's bindings name (root and children), so a step near the cap whose program makes no model call may be stopped; a runbook with such a program and no budget in any binding is refused at submit naming the reason, and so is a budget that is no number of USD of 0 or more, naming the action. A program a person's answer starts (a person action with an `argv`) reserves before it starts and is booked after, also when the run ends right after it; a run whose cap is reached while it takes the last answer of a wait ends (it stayed waiting with nothing open). A reservation of a run that no longer lives counts against no run, and a reservation id does not repeat within a ledger. A cap of another JSON type than a string in `settings`, an out-of-range number such as `1e999` included, is refused naming the cap, over HTTP and through `submit_run`, and the tool description says the caps are strings. `read_run` shows each cap and what is used (`used_wall_seconds`, `used_llm_calls`, `spent_micro_usd`) in `settings`. `docs/daemon-api.md` ("Caps of a run") and `docs/engine.md` say it; the cases hold it (`runbook/tests/daemon/caps.rs`, each under 5 s, no model call).
- A binding names the per-call budget of its programs without the argv, so a runbook whose programs call no model is no longer refused at submit and nothing is passed to a tool that does not take `--max-budget-usd`. The member `max_budget_usd: <number>` of a program action (an action with `executor.argv` or `arguments_from`) is the budget that action's programs reserve, `0` for a program that calls no model; the same member at the top of a bindings file covers every program action of that file that names none itself and not a child file an `open` action names. The order is `--max-budget-usd` in the argv, the action's member, the file's member, the largest budget of the runbook (argv values and members). A runbook whose every program has a budget from one of these needs no budget elsewhere; one with a program that has none and no budget anywhere is refused as before. Refused at submit (daemon) and at load (`runbook run`), naming the action or the file: a member that is no YAML number of 0 or more, an action whose argv and member name two budgets, a member on an action that runs no program; `runbook check` names the same.
