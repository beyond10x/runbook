# Runbook 0.9.0

A minor release of 0.8.0, the same day. The settings file of a run is TOML (it was JSON). The daemon's page
starts a run: the daemon lists the runbooks it can start, and its page opens a form (runbook, intake, a
confinement level the person picks) that sends `submit-run`. `scripts/check-bindings.sh --exits <root>`
checks the exits of a runbook in another repository. The ESS pin is 0.98.0. A source release at tag `0.9.0`;
nothing is published to crates.io, there is no binary asset and no interface is stable. `CHANGELOG.md` lists
the changes with their sources. Read `docs/releases/0.8.0.md` for the release this one follows.

### What this release holds

- **The settings file of a run is TOML** (story `run-settings-are-toml`). `runbook run --settings <file>`
  reads TOML and nothing else, and each setting has one place: the members that lived under the `loom` object
  are at the top level, and `decider`, `models.<role>`, `efforts.<role>` and `review` are tables. An unknown
  key, a key in its old place and a number that is not a whole number where one is asked for are refused by
  name before the run does anything that costs money. `docs/loom-run-settings.md` has the table of places and
  one complete file; `sdc-experiment run` writes `settings.toml` (its `--print` shows the file after
  `settings:`; the experiment records keep their keys). The records of a run (`settings.json`,
  `run-settings.jsonl`) stay JSON with the members and values they had.
- **The daemon has a view of the runbooks it can start.** `GET /daemon/views/runbooks` lists them by name,
  version and runtime: from `--runbook-home` under `--runtime loom`, from the stub's scripts and
  `--runbook-dir` under the stub runtime. It sits behind the daemon's one token check, adds no command, and a
  row holds no path of the host (`docs/daemon-api.md`; ESS entity `Runbook`, view `Runbooks`).
- **The daemon's page starts a run.** The header of the page names its mode: "watch" when the inspector
  (`ui/server.mjs`) serves it, "operate" when the daemon serves it (`runbook serve --ui`). In operate mode the
  button "Start a run" opens a form (`ui/daemon/start.js`) with a runbook from that view, the intake as text
  and a confinement level, and Start sends `submit-run`. What the form never does (`docs/daemon-api.md`, "The
  web UI"): it presets no level (the person picks one from the levels at or above the daemon's floor, and Start
  stays disabled until then); it keeps the token in the memory of the page and empties the field when the form
  closes; it never sends a level below the floor it read, and a level below the daemon's floor starts no run
  (the daemon refuses it `below-floor`, which is the guard); it never replaces a runbook that the list no longer has
  with another. A press repeated after an answer that is not the command's whole answer carries the same
  idempotency key, so no second run starts. Under the stub runtime the form says the run is scripted and
  nothing is executed.
- **`scripts/check-bindings.sh --exits <root>` checks the exits of a runbook in another repository.** Over the
  bindings of any root it no longer reports this repository's five pool bindings as missing; a file it
  cannot read as a bindings file (no bytes, a dangling link, no `actions` list, an `exits` of the wrong type)
  is refused by one line that names the file, exit 1, and a file that `yq` cannot write as JSON is not covered
  (`docs/loom-bindings.md`, `driver/tests/check_bindings_exits*.rs`).
- **The ESS pin moves from 0.97.4 to 0.98.0** (`driver/ess-pin.json`, tag `0.98.0`). `ess specify validate`
  passes with the specification unchanged; the synthesized suite `ess/generated/conformance/suite.json` holds
  118 scenarios (112 with 0.97.4): six added for `OpenSession`, `StartDaemon` and `SubmitRun`, none removed. The
  JSON Schema and the OpenAPI output are byte-identical.
- **For contributors: the driver test step pays each expensive step once.** The `decision_request` tests read
  the committed `ess/generated/schema` instead of running `ess generate`, and the conformance tests resolve
  the pinned `ess` once per test and compile a fixture once per directory.

`runbook --version` prints 0.9.0.

### Breaking

- **The settings file is TOML.** A file that `--settings` names and that is JSON is refused by its content
  before anything starts (exit 2, nothing written). To migrate a JSON file, write the same settings as TOML,
  take the members of the `loom` object to the top level (`loom.sha256` is `loom_sha256`; `in_process`,
  `confinement`, `cap_micro_usd` and `login_file` keep their name) and leave `decider`, `models.<role>`,
  `efforts.<role>` and `review` as tables; `loom.bin` is not a setting (the binary is the option `--loom`).
  The refusal, as printed by this tree for a JSON file (`<file>` stands for the path that was given):

  ```
  runbook run: refused: --settings <file>: this is JSON, and the settings file is TOML now: write the same members as TOML, the members that were under `loom` at the top level (the form and an example: docs/loom-run-settings.md)
  ```

  A TOML file that still has the `loom` table is refused with the new place named:

  ```
  runbook run: refused: loom: there is no `loom` table in the TOML form: loom.sha256 is now `loom_sha256` (docs/loom-run-settings.md)
  ```

  Both end exit 2 with nothing written. The name of the file does not matter: the runner reads its content.
- **`sdc-experiment run` writes `settings.toml`, not `settings.json`,** in the launch directory of a run, and
  the members of the recorded copies stand in the order of the settings file (for a file `sdc-experiment`
  wrote, that order differs from 0.8.0). A reader of `settings.json` or `run-settings.jsonl` that
  reads by member name is not affected; one that reads by position is.

### How to try it

There is no binary to download: build from the checkout (`README.md`, "Try it"). Each `--help` below was run
on this tree.

1. Build: `cd driver && cargo build --locked --bins`, then `cd runbook && cargo build --locked`.
   `runbook --version` prints 0.9.0.
2. `runbook run --help` describes `--settings <FILE>` as "the run settings (TOML)". `docs/loom-run-settings.md` has a complete file to
   start from.
3. The daemon's page: `runbook serve --principal person:operator --ui --token-file <file>` (`runbook serve
   --help`), open the address it prints, press "Start a run", pick a runbook, type an intake, pick a level,
   press Start. The header says "operate". `cd ui && node server.mjs --port 7490 <run directory>/store`
   serves the inspector, whose header says "watch" and which has no form.
4. `scripts/check-bindings.sh --exits <root>` checks the exits of `<root>/bindings/*.yaml`; the exit is 0
   when every binding states its lists.
5. Check the release: `task release:check VERSION=0.9.0`, and the experiment records with
   `sdc-experiment check --all`.

### Numbers

- `ess/generated/conformance/suite.json` holds 118 scenarios (`jq '.scenarios | length'`).
  The commit that moved the pin counts 95 refusals among them (101 of 112 with 0.97.4); this note did not
  count them again.
- The bindings hold 50 program bindings with `exits.error` and 14 model nodes with `exits.not_called`, as in
  0.8.0 (`docs/loom-bindings.md`, "The exit lists").
- `cycles/tree-suite.yaml` holds 55 cycles: 40 converted and 15 pending, as in 0.8.0.
- No count and no time of a test step is claimed here: the machine that prepared this note did not run the
  test steps (its load average was 70 to 110, and a test step ends over its 120 s budget there); the forge
  runs them on the pull request. No test of the tree reads the version.

### Limits

- **No evaluation run was made on this code.** The records of `experiments/` ran on earlier code; this
  release claims no measured change over 0.8.0.
- **The Loom pin is unchanged since 0.8.0** (`c9b4c177`, `runbook/Cargo.toml`). A rejection still gives the
  writer no new allowance of runs: `decider-rework-spent` and `rework-fresh-allowance` stay `pending` and
  `budget.max_runs` counts every run of an action in a case (`docs/cycles-suite.md`).
- **Money caps are as in 0.8.0.** `runbook run` takes `--cap-micro-usd`, `--max-llm-calls` and
  `--max-wall-seconds` as required options (`docs/loom-run.md`); a file never sets or lowers the confinement
  level, and a cap in the settings file must equal the option.
- **A run started from the daemon's page or over MCP has no wall-time bound of its own.** The engine starts a
  run with no `max_wall_seconds` (`runbook/src/engine/calls.rs`, `run_settings`), and neither the form nor
  `submit_run` takes a cap; a run ends by its outcome or by `cancel-run`. Its products are read on disk under
  the daemon's state directory (`runs/<run_id>/` and `workspaces/<run_id>/`, `docs/daemon-api.md`): no tool or
  route serves them yet, and served by the daemon the Products tab says "the daemon serves no files of a run
  yet".
- **The daemon runs a stub unless asked.** `runbook serve` runs the stub runtime, in which nothing is
  executed, unless `--runtime loom` is given (`--runbook-home` names the directory with `protocol/` and
  `bindings/`; `docs/engine.md`). A runbook the view lists under the stub runtime and that the stub has no
  script for is accepted and its run ends `FailedToStart`. The daemon's default confinement floor is `linux`
  and `local` must be asked for by name; a `submit-run` command without the member `confinement` runs at
  `linux` (the form always sends the person's pick).
- **The cycles that run `change.review` and the request entries are not observed as `expected` here.**
  `docs/cycles-suite.md` says that no entry changed from expected to another state is not observed on the
  host where they were run (seven of eight ended on Loom's 60 s bound at a one-minute load of 94 to 156); it
  needs one run of the suite at a load where a cycle ends inside the bound, and that run has not been made.
- **No statement about speed, quality or cost goes beyond `experiments/`.** A figure in these notes is a count
  read from the tree or from a command named above.
- **No binary asset.** A user builds from the checkout.
- **The inspector is read-only and has no route to the daemon.** It starts no program, takes no decision and
  sends no command to the daemon (`ui/README.md`); the page that starts a run is the daemon's own.
- **`sdc-experiment` does not carry an effort.** It refuses `efforts.*` in a `loom` variant; `sdc-node
  --effort` and the settings file of `runbook run` do carry one.
- **`--confinement local` is unconfined** (`docs/loom-run.md`): a bound program can write the whole run
  directory.
- **The rule approver, the rework cap of the old driver and the end by rule `withhold` are not in the runner**
  (`docs/loom-run-decisions.md`).
- `task check:ess-suite:slow` (the byte comparison of a new synthesis with the committed suite), the slow
  lane `task test:cycles-loom` and `task docs:test` were not run for this release.
