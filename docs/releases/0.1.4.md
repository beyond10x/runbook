# sdc 0.1.4

A patch release after 0.1.3, the same day: an observation, data and docs. No rule of a protocol
changed. A source release at tag `0.1.4`; nothing is published to crates.io and no interface is
stable. `CHANGELOG.md` lists the changes with their commits.

### The free-running agent comparison: hypothesis contradicted

The record `free-agent-0.1.0` was registered before its first run with the hypothesis that one
free-running agent, given the same idea and the same list of deliverables, costs more than the SDC
run on 0.1.0 (`run.cost_usd` and `run.tokens_total`). It is contradicted on all four pairs: every
free run costs less than every SDC run, in dollars and in tokens.

| | free agent (Sonnet, one session) | SDC strong | SDC mixed |
|---|---|---|---|
| `run.cost_usd`, median [min, max] (n) | 0.470 [0.414, 0.478] (3) | 5.503 [5.432, 6.194] (3) | 2.549 [2.497, 3.883] (3) |
| `run.tokens_total`, median [min, max] (n) | 413,432 [405,147, 435,634] (3) | 3,260,861 [3,182,911, 4,705,034] (3) | 3,046,058 [2,556,660, 4,191,346] (3) |
| `run.wall_s`, median [min, max] (n) | 164 [145, 176] (3) | 1,247 [1,075, 1,430] (3) | 1,489 [1,480, 2,091] (3) |
| clean passes | 3 of 3 | 3 of 3 | 3 of 3 |

Figures from `experiments/free-agent-0.1.0/report.md`.

- The free agent delivered a smaller product: 449 to 604 product lines with 16 to 19 tests and 4 or
  5 requirements, against 977 to 1,527 product lines with 25 to 50 tests and 5 to 7 requirements
  for the six SDC runs (`experiments/free-agent-0.1.0/sizes.json`).
- Each side wrote its own specification, so the suites differ (8 to 13 scenarios for the free
  agent, 14 to 20 for the SDC) and conformance does not rank them. The free products' own figures:
  6 of 8, 10 of 11 and 10 of 13 scenarios proven passed.
- The quality of both sides' products was evaluated blind; the next section has the result.
- The confounds (decider, shell, adapter, what counts as delivery, tree, builds, network) are in the
  report and in `docs/llm-is-not-the-runtime.md`.

### The blinded quality evaluation

The nine products were scored in a real browser on blinded copies, against a 23-item rubric
written from the idea text before any product was opened (`docs/quality-0.1.0.md`,
`experiments/quality-0.1.0/scores.json`).

| side | score, median [min, max] of 23 | product lines | own tests | cost USD | wall s |
|---|---|---|---|---|---|
| SDC strong | 23 [20, 23] | 1450 [1356, 1666] | 42 [25, 50] | 5.503 [5.432, 6.194] | 1247 [1075, 1430] |
| SDC mixed | 22 [20, 23] | 1335 [1086, 1651] | 37 [34, 38] | 2.549 [2.497, 3.883] | 1489 [1480, 2091] |
| free agent | 20 [19, 20] | 663 [623, 763] | 17 [16, 19] | 0.470 [0.414, 0.478] | 163 [143, 173] |

- The sides differ on three items (passes out of 3, strong / mixed / free agent):
  - F3, edit a task: 2 / 2 / 0.
  - F5, remove a task: 3 / 2 / 0.
  - O7, conflicting offline edits: 2 / 2 / 0. This item needs edit, and no free product has an edit
    or remove control.
- S3, live update within 10 s, passed 2 / 2 / 2. Every other item passed in all nine products.
- The exploration found four defects, all in SDC products:
  - mixed-1 does not send a change made while the server is unreachable.
  - mixed-3 joins text typed during a slow add to the previous title.
  - strong-1 ignores a title that already exists.
  - strong-2's README starts a partial binary first.
- No defect was found in the free products, which also offer fewer controls that can go wrong.
- Limits:
  - One idea, three products per side, and the rubric is one reading of the idea text.
  - Two browser contexts on one machine stand in for two people, and offline is emulated.
  - A browser test sees behaviour, not code quality.
  - Blinding held for file names and run data, not for style.
  - No significance claim is made.

### The conformance observation

`sdc-conform observe` holds a delivered product to the suite of its own run's specification and
writes `oracle.json` (`docs/conformance.md`). The figure is a lower bound: a scenario counts passed
only when every counted table that reached it passed it, and what the tables could not reach stays
outside the count. It is judged against the run's own specification, the contract the run wrote and
then implemented, and decides nothing. ESS 0.97.0 is pinned by sha256 (`driver/ess-pin.json`).

The six 0.1.0 baseline products (`experiments/baseline-0.1.0/conformance/`):

| run | spec scenarios proven passed (lower bound) |
|---|---|
| `trial-0.1.0-strong-1` | 16 of 17; 1 failed; 0 not measurable |
| `trial-0.1.0-strong-2` | 11 of 17; 2 failed; 4 not measurable |
| `trial-0.1.0-strong-3` | 7 of 20; 13 failed; 0 not measurable |
| `trial-0.1.0-mixed-1` | 6 of 19; 5 failed; 8 not measurable |
| `trial-0.1.0-mixed-2` | 2 of 16; 8 failed, all 8 refused for a precondition the specification does not model; 6 not measurable |
| `trial-0.1.0-mixed-3` | 11 of 14; 2 failed; 1 not measurable |

### The cost target

- The operator set it from the comparison: "so, this is our target then 10% costs". The target is
  `run.cost_usd` 0.47 USD on this input in every setting, delivery and the product check no worse
  (`docs/improving.md` § Target, `experiments/targets.yaml`).
- Where it goes now (`experiments/baseline-0.1.0/costs.md`): strong 5.50 USD, 62 % loading context
  (cache write), 33 % output; mixed 2.55 USD, 55 % and 38 %; 34 model sessions per run against 1.
- By class, strong: decider 2.03, implement 1.98, review 0.75, writer 0.53 USD; the floor with
  today's protocols is about 2.0 USD with Sonnet work nodes.

### What changed

- `sdc-conform` and `sdc-conform-adapter`, with the pinned ESS. The conformance line in
  `sdc-run-metrics` and `sdc-run-compare`, and a conformance column in the progress ledger.
- After a close `scripts/run-trial.sh` can observe conformance. A real observation costs about 1 to
  3 USD of model calls per run, so in this release it is **off by default**:
  `SDC_CONFORMANCE=observe` turns it on, and an experiment record turns it on explicitly with the
  launch setting `conformance: observe`. A recorded re-drive never observes, and the stub trial
  costs nothing. This is the only change to what a run does by default.
- `sdc-free-agent` and the record `free-agent-0.1.0` with its run summaries, timelines, sizes and
  conformance; `docs/llm-is-not-the-runtime.md`.
- The analysis of the 0.1.0 baseline (`losses.md`, `costs.md`, `inputs.md`, `models.md`), the cost
  target in `experiments/targets.yaml`, and three records registered before any run:
  `build-constraints`, `review-haiku-replay`, `review-minimal-facts`.
- The blinded quality evaluation: `docs/quality-0.1.0.md`, `experiments/quality-0.1.0/` (rubric,
  scores, screenshots) and its Playwright harness under `eval/quality/`.
- The site: the conformance chart on Evaluation; the free-agent comparison and the quality section
  on "The LLM is not the runtime".

### Checks on this tree

- `scripts/run-finding-cycles.sh`: 99 expected cycles and 2 pending (`rework-spent-dropped`,
  `rework-spent-abandoned`). The new cycle `conformance-default-off` checks that a run does not
  observe conformance by default.
- The conformance tests in `driver/tests/conformance.rs` need the pinned ess installed
  (`sdc-conform ess-install`, which verifies the archive's sha256). CI does not run them; they
  passed in the merge gate.
- `scripts/check-bindings.sh`, `sdc-experiment check --all`, `task docs:build` and `task docs:test`.

### Limits

- The started product is not confined: it runs on the host as the operator's user, from a copy of
  the delivered tree with a cleared environment.
- Events are built from the response body, so event checks test the table as much as the product.
- Each table is a model's reading of the product. Several tables make a disagreement visible but do
  not resolve it, and a table can still pass a scenario the product fails.
- Only products with an HTTP JSON surface can be observed.
- A capture reads only what the product prints.
- No run has used the 0.1.2, 0.1.3 or 0.1.4 tree.
- Nobody started the delivered product by hand.
- The driver's runtime parts are a temporary copy of what the Loom runtime must provide.
