# Runbook 0.9.1

A patch release of 0.9.0, the same day. `scripts/install.sh --prefix <dir>` lays out an installed runbook: the
`runbook` command, the helper programs a run starts and the files it reads, under one directory you name.
`runbook --version` prints the version and the commit of the build. A `runbook` started from an installed
prefix puts `<prefix>/libexec/runbook` in front of the `PATH` of the programs it starts. Nothing is marked
breaking. A source release at tag `0.9.1`; nothing is published to crates.io, there is no binary asset and no
interface is stable. `CHANGELOG.md` lists the changes with their sources. Read `docs/releases/0.9.0.md` for
the release this one follows.

### What this release holds

- **`scripts/install.sh --prefix <dir>` installs runbook from a checkout** (`README.md`, "Try it";
  `docs/releasing.md`, "The binary"). It builds `runbook`, the programs a run starts (`sdc-answers`,
  `sdc-bugfix`, `sdc-check-routes`, `sdc-conform`, `sdc-conform-adapter`, `sdc-decision-request`,
  `sdc-findings`, `sdc-node`, `sdc-replay`, `sdc-reply`) and `sdc-watch` with `cargo build --locked --release`,
  and writes `<dir>/bin/runbook`, `<dir>/libexec/runbook/<helper>` and `<dir>/share/runbook/` (the protocols,
  bindings, instructions, views, cycles, scripts, tools and the files of the page, `VERSION` and `MANIFEST`,
  the list of every file it wrote). The installed `runbook` runs from any directory and needs no checkout:
  `runbook doctor` lists what it found and what is missing. At its end the script prints one line for bash,
  one for zsh and one for fish to put `<dir>/bin` on `PATH`; it changes no shell profile and writes nowhere
  else. A second run over the same prefix updates it: a file the old `MANIFEST` lists that the new one does
  not is removed, and nothing else. `--from-built debug|release` takes binaries that exist already instead of
  building.
- **`runbook --version` prints the version and the commit of the build** (`runbook 0.9.1 (<commit>)`):
  HEAD of the repository that tracks `runbook/Cargo.toml`, `unknown` outside git. `VERSION` in the prefix
  holds the same commit and ends in ` dirty` when `git status` reports a change of a tracked file.
- **An installed `runbook` finds its helpers.** From a prefix (its directory is named `bin`, and
  `libexec/runbook` and `share/runbook/protocol` are directories) it puts `<prefix>/libexec/runbook` in front
  of the `PATH` of the programs it starts, so a bound tool that starts `sdc-reply` or `sdc-findings` finds it
  without anything but `<dir>/bin` on the user's `PATH`.
- **`runbook doctor` says `incomplete install`** for a prefix that is half installed (the marker
  `share/runbook/INSTALLING` is there, `VERSION` or `MANIFEST` is missing, or a file `MANIFEST` names is
  missing); a `runbook` started from the `bin` of such a prefix runs nothing from a checkout.
- **For contributors:** `task test:install` is the slow lane that builds the real release prefix and runs
  `runbook list`, `runbook doctor` and the dry run `runbook run sdc --dry` from it; the fast lane is
  `runbook/tests/install/`.

### What the install script refuses

Each refusal ends exit 2 with nothing written; `scripts/install.sh --help` lists the rest. Printed by this
tree (the first line of each):

```
install.sh: --prefix <dir> is required
install.sh: the prefix must be an absolute path, not relative
install.sh: the prefix is the root directory: name a directory of your own
install.sh: the prefix /nonexistent-dir-x does not exist as a directory: make it first
```

It also refuses a prefix inside `~/.cargo`, inside a copied directory of the checkout, the checkout itself, a
directory that holds it or its `.git`, and a name with a newline. In a git work tree it copies only the files
git tracks, and a checkout whose `.git` git cannot be asked about (another owner, no git, a broken
repository) is refused with the reason and nothing is written. From a source archive (no `.git`) it copies the
regular files that are not dot-files. It stops for a target triple (`CARGO_BUILD_TARGET`, `build.target`):
it installs no cross build.

### Breaking

None is marked. One behaviour changed, and it is named here because it removes a lookup:

- **Helper programs are read from `<prefix>/libexec/runbook`, no longer from the flat `<prefix>/libexec`.**
  `runbook doctor` and the runner look there (`docs/cli.md`). `libexec/runbook` belongs to this product, so
  nothing another package keeps in `<prefix>/libexec` is found through it. A user who laid helpers out by hand
  directly in `<prefix>/libexec` moves them to `<prefix>/libexec/runbook`, or installs with the script, which
  writes there. Before 0.9.1 no script laid out a prefix.

### How to try it

There is no binary to download: build from the checkout. Each command below exists in this tree.

1. `scripts/install.sh --help` prints the usage and the limits.
2. Make a directory and install into it: `scripts/install.sh --prefix <absolute dir>` (it builds in release
   mode, which takes minutes).
3. Put `<dir>/bin` on `PATH` with the line the script printed for your shell, then `runbook --version`
   (version and commit) and `runbook doctor`.
4. A dry run from the prefix: `runbook run sdc --dry --intake <idea file> --run trial-dry --runs-dir runs
   --settings <settings.toml> --confinement local --spend-ledger <ledger file> --cap-micro-usd <n>
   --max-llm-calls <n> --max-wall-seconds <n>` (`README.md`, "Try it"; `docs/loom-run-settings.md` has a
   settings file to start from).
5. Check the release: `task release:check VERSION=0.9.1`, and the experiment records with
   `sdc-experiment check --all`.

### Numbers

- The suite `ess/generated/conformance/suite.json` holds 118 scenarios and `cycles/tree-suite.yaml` holds 55
  cycles, 15 of them pending (`yq '.cycles | length'`); both as in 0.9.0. The ESS pin is 0.98.0 and the Loom pin
  `c9b4c177`, as in 0.9.0.
- The script lists 10 helper programs and `sdc-watch`, as above.
- No count and no time of a test step is claimed here: the machine that prepared this note did not run the
  test steps (its load average was 70 to 110, and a test step ends over its 120 s budget there); the forge
  runs them on the pull request. No test of the tree reads the version.

### Limits

- **No binary asset.** A user builds from a checkout, now with the install script; the script is the source
  of an asset that does not exist yet (`docs/releasing.md`, "The binary").
- **The script builds on the machine it runs on and installs from the checkout it lies in.** It copies only
  files git tracks (a file that is not tracked is not installed) and refuses a checkout whose git cannot be
  asked. Two installs at once into one prefix are not held apart; an install from an archive lacks the links and
  dot files of a git checkout; a release install after a branch was moved from another work tree is refused
  until an input of the build changes; a checkout with the reftable format cannot be installed (its commit is
  unknown); the modes of `bin`, `libexec` and `share` are the ones they have. `scripts/install.sh --help` has
  each.
- **No evaluation run was made on this code.** The records of `experiments/` ran on earlier code; this
  release claims no measured change over 0.9.0.
- **The Loom pin is unchanged since 0.8.0** (`c9b4c177`, `runbook/Cargo.toml`). A rejection still gives the
  writer no new allowance of runs: `decider-rework-spent` and `rework-fresh-allowance` stay `pending` and
  `budget.max_runs` counts every run of an action in a case (`docs/cycles-suite.md`).
- **Money caps are as in 0.8.0.** `runbook run` takes `--cap-micro-usd`, `--max-llm-calls` and
  `--max-wall-seconds` as required options (`docs/loom-run.md`); a file never sets or lowers the confinement
  level, and a cap in the settings file must equal the option.
- **A run started from the daemon's page or over MCP has no wall-time bound of its own.** The engine starts a
  run with no `max_wall_seconds` (`runbook/src/engine/calls.rs`, `run_settings`); a run ends by its outcome or
  by `cancel-run`. Its products are read on disk under the daemon's state directory (`runs/<run_id>/` and
  `workspaces/<run_id>/`, `docs/daemon-api.md`): no tool or route serves them yet.
- **The daemon runs a stub unless asked.** `runbook serve` runs the stub runtime, in which nothing is
  executed, unless `--runtime loom` is given (`docs/engine.md`).
- **The cycles that run `change.review` and the request entries are not observed as `expected` here.**
  `docs/cycles-suite.md` says that no entry changed from expected to another state is not observed on the
  host where they were run; it needs one run of the suite at a load where a cycle ends inside Loom's 60 s
  bound, and that run has not been made.
- **No statement about speed, quality or cost goes beyond `experiments/`.** A figure in these notes is a count
  read from the tree or from a command named above.
- **The inspector is read-only and has no route to the daemon** (`ui/README.md`).
- **`--confinement local` is unconfined** (`docs/loom-run.md`): a bound program can write the whole run
  directory.
- `task check:ess-suite:slow`, the slow lane `task test:cycles-loom`, `task test:install` and `task docs:test`
  were not run for this release.
