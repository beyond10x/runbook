# Runbook 0.9.2

A patch release of 0.9.1, the same day. `runbook run` writes `runner.json` into the run directory and one
`action_started` line in `events.jsonl` when an action starts, before its program ends. The inspector shows the
step in flight of such a run, tells a live runner from one that is gone and says why a `runner.json` was not
read. The Now band no longer shows a live run as "Stopped: step budget spent" between two steps. Nothing is
marked breaking. A source release at tag `0.9.2`; nothing is published to crates.io, there is no binary asset
and no interface is stable. `CHANGELOG.md` lists the changes with their sources. Read `docs/releases/0.9.1.md`
for the release this one follows.

### What this release holds

- **`runbook run` records the step in flight** (`docs/loom-run-directory.md`, "The runner and the step in
  flight"). `runner.json` is written when the run directory is made, before the first step: the pid of
  `runbook run`, the start time the kernel gave that process, when it started and, once the run ended by any exit
  after the run directory exists (a signal it handles included), when it closed. It holds no environment, argv
  or path outside the run directory. `events.jsonl` gets one `action_started` line when an action starts, before
  its program ends. A runner killed by SIGKILL cannot close the file; the inspector tells it by the process.
- **The inspector shows the step in flight.** The Now band says "<action> running since <time>, <n> min",
  "Between steps" or "Not live: last started <action>" (`/api/live` `liveness` is `running`, `between` or
  `not_live`, with `runner` and `step`; `ui/README.md`). It asks the kernel only whether `/proc/<pid>/stat` has
  the recorded start time: no signal is sent and no permission is needed beyond the read of `/proc`. When it
  does not read a `runner.json` (over 4 KiB, not a regular file, more than one name, not a record) it says
  "runner.json was not read: …" with the reason, and not that the runner writes no record of a live process.
- **The Now band no longer says "Stopped: step budget spent" between two steps.** `runbook run` makes each step
  `tree run --max-steps 1`, and Loom ends every such step with the case event `step_budget_spent`; the band read
  that event as a stop of the case. For a run with `runner.json` it is the end of a step: the band says
  "Between steps" while the runner lives and "Not live" when it does not.

### Breaking

None is marked.

### How to try it

There is no binary to download: build from the checkout. Each command below exists in this tree.

1. `scripts/install.sh --help` prints the usage and the limits of the install script (`README.md`, "Try it");
   `scripts/install.sh --prefix <absolute dir>` installs into a directory you made (it builds in release mode,
   which takes minutes).
2. Start a run with `runbook run <runbook> --intake <file> --run <name> --runs-dir <dir> --confinement local
   --settings <settings.toml> --spend-ledger <file> --cap-micro-usd <n> --max-llm-calls <n>
   --max-wall-seconds <n>` (`docs/loom-run.md`); `<dir>/<name>/runner.json` exists
   before the first step.
3. Open the inspector on the runs directory: `node server.mjs --runs <dir>` from `ui/` (`ui/README.md`). While the run
   goes, the Now band names the action and its running time.
4. Check the release: `task release:check VERSION=0.9.2`, and the experiment records with
   `sdc-experiment check --all`.

### Limits

- **No binary asset.** A user builds from a checkout with `scripts/install.sh --prefix <dir>`; the script is the
  source of an asset that does not exist yet (`docs/releasing.md`, "The binary").
- **The install script builds on the machine it runs on and installs from the checkout it lies in.** It copies
  only files git tracks and refuses a checkout whose git cannot be asked. Two installs at once into one prefix
  are not held apart; an install from an archive lacks the links and dot files of a git checkout; a release
  install after a branch was moved from another work tree is refused until an input of the build changes; a
  checkout with the reftable format cannot be installed. `scripts/install.sh --help` has each.
- **Only `runbook run` writes `runner.json`** (`runbook/src/loom_run/run_loop.rs`). A run of the daemon's stub
  runtime, in which nothing is executed, and a run directory an older `runbook` wrote have none, and the
  inspector shows them as it showed them before: "live state unknown" for a directory with `settings.json`, no
  end record and no `runner.json`.
- **The line of the step in flight is not shown.** Loom pipes a bound program's output into its own process and
  returns the last bytes when the program ends; the only file that grows while a step runs is under
  `work/.sdc/llm/`, a dot-directory the inspector never serves (`docs/loom-run-directory.md`).
- **`runner.json` and the start lines are what files of the run directory claim.** Under `--confinement local` a
  bound program can write the run directory, so the inspector's answer is a reading of those files, shown as
  text, and nothing decides on it.
- **No evaluation run was made on this code.** The records of `experiments/` ran on earlier code; this
  release claims no measured change over 0.9.1.
- **The Loom pin is unchanged since 0.8.0** (`c9b4c177`, `runbook/Cargo.toml`). A rejection still gives the
  writer no new allowance of runs: `decider-rework-spent` and `rework-fresh-allowance` stay `pending` and
  `budget.max_runs` counts every run of an action in a case (`docs/cycles-suite.md`).
- **Money caps are as in 0.8.0.** `runbook run` takes `--cap-micro-usd`, `--max-llm-calls` and
  `--max-wall-seconds` as required options (`docs/loom-run.md`); a file never sets or lowers the confinement
  level, and a cap in the settings file must equal the option.
- **A run started from the daemon's page or over MCP has no wall-time bound of its own.** The engine starts a
  run with no `max_wall_seconds` (`runbook/src/engine/calls.rs`, `run_settings`); a run ends by its outcome or
  by `cancel-run`. Its products are read on disk under the daemon's state directory (`runs/<run_id>/` and
  `workspaces/<run_id>/`, `docs/daemon-api.md`): no tool or route serves them yet.
- **The daemon runs a stub unless asked.** `runbook serve` runs the stub runtime, in which nothing is
  executed, unless `--runtime loom` is given (`docs/engine.md`).
- **The cycles that run `change.review` and the request entries are not observed as `expected` here.**
  `docs/cycles-suite.md` says that no entry changed from expected to another state is not observed on the
  host where they were run; it needs one run of the suite at a load where a cycle ends inside Loom's 60 s
  bound, and that run has not been made.
- **No statement about speed, quality or cost goes beyond `experiments/`.** A figure in these notes is a count
  read from the tree or from a command named above.
- **The inspector is read-only and has no route to the daemon** (`ui/README.md`).
- **`--confinement local` is unconfined** (`docs/loom-run.md`): a bound program can write the whole run
  directory.
- `task check:ess-suite:slow`, the slow lane `task test:cycles-loom`, `task test:install` and `task docs:test`
  were not run for this release.
