# Runbook 0.4.1

A patch release of 0.4.0, the same day: one fix, checks and tools, and two records. It changes no
protocol and no behaviour of the product. A source release at tag `0.4.1`; nothing is published to
crates.io and no interface is stable. `CHANGELOG.md` lists the changes with their sources. Read
`docs/releases/0.4.0.md` for the release this one follows.

### What this release holds

- **A fix in `runbook loom-run`.** A model step that ended before it started any adapter (its call
  directory has no `request.json` and a `status.json` with the step's exit) costs nothing: the
  reservation is released, the event `no_model_call` names the call and the exit, and the run goes on
  with what Loom says of the step, where it ended `error` at the cost reader. A call directory with a
  `request.json` and no cost record, and one without a readable `status.json` exit, stay fail-closed
  (`docs/loom-run.md`).
- **ESS 0.97.3.** The specification pins it (`requires: ess 0.97.3` in `ess/ess-inputs.yaml`), the
  synthesized conformance suite of the daemon is committed (`ess/generated/conformance/suite.json`,
  114 scenarios, suite version `ess-conformance/40`, and `DIGEST`) and its digest check is part of
  `task check:ess-generated`; `task check:ess-suite:slow` synthesizes it again and compares bytes. The
  digest no longer hashes what the host's `ess --version` prints. `driver/ess-pin.json` pins 0.97.3
  instead of 0.97.0, and the product checks of a run (`bindings/tools/sdc-tool.sh`, `ESS_TOOLCHAIN`)
  run 0.97.3 instead of 0.96.0. Runs and recordings made before carry 0.96.0
  (`story:daemon-synthesized-suite-has-no-refusal`).
- **A reference check.** `sdc-check-unreferenced` (`task check:unreferenced`, part of `task check`)
  lists the tracked files of the tool directories that no other tracked text file refers to and exits
  1 when there are any. `--without <path>...` lists the files that only the given paths refer to.
  `driver/unreferenced-keep.txt` holds 26 files the first run found, unexamined; nothing is deleted.
- **Two evaluation tools read a Loom run.** `sdc-finding-kpis` and `sdc-run-timeline` read the run
  directory of `runbook loom-run` as well as the driver's, detected from its files, with the same
  output shape. A figure a Loom directory has no source for is `null` with a reason, and a directory
  of neither kind is refused with exit 2 (`docs/loom-run-directory.md`, "The two evaluation tools").
- **UI test children end with their parent.** Every server, fixture player and daemon a UI spec starts
  goes through `ui/test/child.mjs`, whose guard ends the child's process group when the process that
  started it is gone, also after SIGKILL (`story:ui-test-servers-end`). A server started by hand is
  unchanged.
- **Records.** `experiments/parity-loom-strong-3.yaml`: three runs through Loom with the decider's
  answers declared in `bindings/tools/answers.yaml`. And the result of
  `experiments/release-0.3.1.yaml`: nine runs, eight closed and one stopped at `writer_spent`. Both
  are descriptive; see "The records".

`runbook --version` prints 0.4.1.

### How to try it

The binaries are built with `cargo build --bins` in `driver/` and `runbook/`. Each `--help` below was
run on this tree.

1. Check that no tracked file of the tool directories is unreferenced: `task check:unreferenced`
   (about 2.6 s here), or `driver/target/debug/sdc-check-unreferenced`. `--help` prints the scope and
   the rules, `--without <path>...` the files a deletion would leave unreferenced.
2. Read a Loom run with the evaluation tools: `sdc-finding-kpis <run dir> --json` and
   `sdc-run-timeline <run dir> --check`. Both print their usage on `--help`.
3. Check the committed ESS output and the committed suite's digest: `task check:ess-generated`.
4. Check the release: `task release:check VERSION=0.4.1`, and the experiment records with
   `sdc-experiment check --all`.

The daemon (`runbook serve`) and `runbook loom-run` are used as in `docs/releases/0.4.0.md`.

### Numbers

- The synthesized suite holds 114 scenarios (`jq '.scenarios | length'` of `suite.json`).
- `sdc-check-unreferenced` ran in 2.6 s of wall time on this tree, 26 lines in
  `driver/unreferenced-keep.txt` and 10 in `driver/unreferenced-whole.txt`.
- The test steps of `task check` were not run for this note; the forge's `Shared source gates` run
  on the release commit is their gate. No test time is claimed here.

### Limits

- The daemon runs cases on its stub runtime only; the engine that runs a case on Loom inside the daemon is not in this release.
- `runbook loom-run` needs a `b10x-loom` binary built from a Loom commit that is not published; the tree pins `5af3f9c2`.
- No parity verdict between the driver and Loom exists: no run through Loom has closed. The three runs of `parity-loom-strong-3` passed `scope.answer` and ended at a finding with no declared request (1) and at `change.review` exiting 2 under Loom (2); the three of `parity-loom-strong-2` stopped at `scope.answer`.
- The fix of a step that ended before any adapter is tested on a hand-made call directory only; no run through Loom has used it, and `change.review` still exits 2 under Loom: this release does not change what the step reads.
- The driver and its scripts are still the default runner of every experiment record.
- The full set of finding cycles was not run on this tree; the last full runs were on `8bddf508` and `b44f99b9b` (126 of 127 expected cycles as expected, `pool-wait` failed; fixed in `4133330ac`, not run again in full; `docs/releases/0.3.1.md`, "Checks").
- `task check:ess-suite:slow`, the byte comparison of a new synthesis with the committed suite, was not run for this release; the fast digest check is.
- No run has used this tree, and the release claims no measured change: `experiments/releases.yaml` has no line for 0.4.1. A comparison of runs across the move from ESS 0.96.0 to 0.97.3 has to say so.
- The 26 files in `driver/unreferenced-keep.txt` are unexamined.
- Every limit of 0.3.1 that this note does not change stands, among them that under Loom the exits 69 and 70 are recorded as `failed` (`bindings/PENDING.md`) and that the comparison of the stub cycle covers no run with a model.
