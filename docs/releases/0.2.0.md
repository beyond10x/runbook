# Runbook 0.2.0

The first release under the name Runbook, the same day as 0.1.4. The product is now called Runbook;
the software delivery cycle (SDC) is its first runbook and keeps its name and every id. The
repository and the site move to the new name. The release also carries a fix of the spec gate, the
results of the nine `release-0.1.2` runs and a reworked documentation site. No protocol or binding
changed; one tool's check got stricter. A source release at tag `0.2.0`; nothing is published to
crates.io and no interface is stable. `CHANGELOG.md` lists the changes with their commits.

### The name: Runbook

- **Runbook** is the product: a runbook is a fixed, checked way to handle a case, where a program
  decides the next step from recorded facts and a model carries out single steps.
- **SDC**, the software delivery cycle, is the first runbook. Its protocols (`sdc.*`), the
  binaries (`sdc-drive` and the others), the `SDC_*` environment names, the trial and experiment
  records and the measurements keep their names. Renaming those is a later stage of
  `story:project-rename`.
- The README, `AGENTS.md`, the documentation site and the run inspector use the new name.

### The documentation site

- **The landing page** has a short three-line lede and, below the hero, a slider of three claims:
  what it does (from an idea to a delivered app, with the clean passes of the latest release with
  runs), why it is simple (the next step is computed from recorded facts) and why it is solid
  (every step is recorded and can be replayed). Every number comes from committed data. The slider
  follows the carousel pattern: it can be paused, it does not rotate under reduced motion, and it can
  be driven by keys and by swiping.
- **The evaluation page** opens with headline tiles and large charts instead of method text. The
  tiles show clean passes, median cost and wall time per setting, the cost target with the factor
  still to go, the blinded quality medians and the conformance lower bound. The charts show clean
  passes, cost (with the target and the free-running agent's median), wall time and where the cost
  of a run goes. They are followed by stops by cause, the improvement experiments and every run. A
  chart column exists only for a release with committed runs.
- **A Context page** (`/docs/context`) answers what a model call is given: what one node sees, how
  context passes from node to node, what the program holds, how a reader changes it, what can be
  inspected afterwards, and why. Each statement links to the line of code it rests on.
- **The navbar** has four entries: How it works, Protocols, Evaluation and Run it, with GitHub as
  an icon link. How it works is active on its five pages: What Runbook is, The LLM is not the
  runtime, The flow, Context and Built on. The docs sidebar holds that group in the same order.

### The spec gate

`spec.synthesize` and `spec.gate` (`sdc-tool.sh` `spec_conform`) now run the synthesized suite
against ESS's interpreted target (`ess verify conform run --target interpreted --strict`). A spec
passes only when every scenario passes. An unsupported, failed or errored scenario refuses it, and
`spec.author` gets one line per such scenario. Before, the gate only required that synthesis refused
nothing, so a spec whose own suite did not pass could reach the story, where the implementing writer
cannot change it. `release-0.1.2.mixed.1` stopped `writer_spent` at `change.implement` that way,
with 8 scenarios unsupported ("binding command has an unmet outcome obligation"). The check costs
about 0.04 s more on a baseline-size spec. Cycle `spec-interp-unsupported`; the committed replay
recording is re-packed.

### The release-0.1.2 runs

`experiments/release-0.1.2/report.md` and `notes.md`: nine runs on tree 72a3eef, the to-do idea in
the three baseline settings.

| setting | clean passes | `run.cost_usd`, median [min, max] | `run.wall_s`, median [min, max] | stops |
|---|---|---|---|---|
| strong (Sonnet work, Opus decider) | 3 of 3 | 4.695 [4.460, 4.816] | 972 [886, 1108] | - |
| mixed (Sonnet work, Haiku decider and other nodes) | 2 of 3 | 2.523 [1.373, 3.035] | 1577 [810, 1821] | `writer_spent` in IDEA-1.sharedlist.list |
| Haiku | 2 of 3 | 0.932 [0.882, 1.724] | 3231 [2832, 3278] | `writer_spent` in IDEA-1.list.sync |

These are compared against `baseline-0.1.0` (same input and settings, tree 4468bfd) under the
record's registered rule: a difference is claimed only when the two ranges of three separate
completely.

- **Haiku, primary (P1).** `run.clean` is 2 of 3, against 0 of 3 in the baseline. The record holds
  P1 only at 3 of 3 and calls 1 or 2 of 3 **inconclusive**, so this result is inconclusive.
- **Strong and mixed clean passes (guard P4).** Strong stays at 3 of 3. Mixed fell from 3 of 3 to 2
  of 3, so the guard "run.clean of strong and mixed stays 3 of 3" does not hold for mixed. Its stop
  is the spec defect that this release's gate fix refuses at the spec stage.
- **Strong cost.** 4.46 to 4.82 USD against 5.43 to 6.19 USD: the ranges separate downward. The
  notes trace 2.71 of the 3.16 USD difference to reruns:
  - 5 rather than 12 reruns of `change.implement` and `spec.author`;
  - cheaper remaining reruns;
  - shorter review reads.

  Without reruns, the two trees overlap. No change between the trees makes a first take smaller,
  and with three runs per tree the notes call the separation most likely chance. The registered
  expectation of no separation stands for first-take cost.
- **Mixed cost** (2.523 [1.373, 3.035] against 2.55 [2.50, 3.88]) overlaps; no claim.

### Limits

- Three runs per setting and tree; every claim above follows the record's rule.
- The story's `tests.run` still runs the interpreted suite, so it repeats a check the spec stage now
  passes; removing it is a follow-up.
- The conformance observation after close is off by default (0.1.4). The `release-0.1.2` runs used
  tree 72a3eef, which has no observation, so they carry no conformance figure.
- No run has used the 0.1.3, 0.1.4 or 0.2.0 tree.
- The binaries, environment names and protocol ids still say `sdc`; one `runbook` command is a
  later stage.
- The driver's runtime parts are a temporary copy of what the Loom runtime must provide.
