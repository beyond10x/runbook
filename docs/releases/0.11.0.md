# Runbook 0.11.0

A minor release of 0.10.0. One change is marked breaking: from Loom 0.61.0 a `*` row of a binding's result table no
longer matches a run killed at its timeout. `runbook` links Loom 0.61.0, so a program step may run up to 14400 s; a
bug-fix check runs in a git tree; the cycles suite answers build and test commands from recordings. A source release at
tag `0.11.0`; nothing is published to crates.io, there is no binary asset and no interface is stable. `CHANGELOG.md`
lists the changes with their sources. Read `docs/releases/0.10.0.md` for the release this one follows.

### Breaking changes

- **A `*` row of a binding's result table no longer matches a run killed at its timeout.** From Loom 0.61.0 such a run
  matches only a `timeout` row, and without one ends `ResultNotInTable` and the case may stop `Stuck`. The remedy: add
  a `timeout` row with the result `*` gave to every program binding of your own whose table has a `*` row (the 28
  tables of `bindings/*.yaml` and the test fixtures have it, and the JSON copies in `driver/examples/sdc/` name it
  too).

### What this release holds

- **`runbook` links Loom 0.61.0** (`ed644a4d`, tag `0.61.0`; replaces `d8944d49`), one git rev for every Loom crate;
  `b10x-loom-bindings` is a dependency now, not a dev-dependency. A `program` binding may name `timeout_seconds` up to
  14400 (past 3600 s the program gets 3600/`timeout_seconds` of one core; every other executor keeps 3600, and a
  `handoff_when` check or an `arguments_from` program runs under at most 3600 s), a `ProgramError` refusal ends with
  the program's stderr tail, and a program whose run allowance is spent gets its `from: runs` record
  (`docs/loom-bindings.md`, "Timeouts"). Loom's own ESS pin is 0.98.1; Runbook's stays 0.98.0 and no generated file
  changes.
- **`runbook check` names a `timeout_seconds` past its executor's range** in Loom's words (1 to 14400 on a `program`,
  1 to 3600 on any other executor; `TimeoutOutOfRange`), where it named none and only the opening of a run refused the
  file.
- **A bug-fix check runs in a git tree** (`docs/bugfix.md`, "The trees a check runs in are git trees"). The copies of
  `impl/` and of the base under `.sdc/bugfix/` that `repro-run`, `tests-run` and `gate-run` run the commands of
  `checks.yaml` in are git repositories with one commit of the copied files, because the build pool's remote mode needs
  a git repository in a job's tree. The fix's diff, the artifacts and their bytes are unchanged; git must be on `PATH`
  (without it the step exits 127).
- **A bug-fix check whose pool job exits 127 or 126 is a program error of the step,** exit 127 or 126 with a line that
  names the command, and no verdict; `repro-run` read it as `not red`.
- **The bug-fix runbook's `gate.run` names `timeout_seconds: 4200`,** the limit its pool wait and four pool jobs need.
- **`scripts/check-bindings.sh` takes `timeout` as a key of a `from: exit` result table** beside the exit codes and
  `*`.
- **The cycles suite (`task test:cycles-loom`) builds nothing.** The `slot` first on the `PATH` of its programs is
  `sdc-recorded-pool`, which answers each build and test command from a recording in `cycles/recorded/`; a command with
  no recording is a program error whose line names the digest, and the slow lane `task test:cycles-record` records it
  (`docs/cycles-suite.md`, "Recorded build and test results"). `runbook doctor` names `sdc-recorded-pool` as an
  optional helper.
- **`sdc-conform-adapter` holds the port it tells a product** until the product ends, so no other process is given it;
  a product that cannot bind a held port is started once more on another port, logged `port_not_held`
  (`docs/conformance.md`, "The adapter").
- **The forge's log of `task test:runbook` shows the runner's output again:** the nextest output, the ten slowest and
  the budget line. `task check:task-output` is part of `task check`; `task check:task-output:forge` is the lane to run
  when a shell block of the Taskfile changes.

### How to try it

There is no binary to download: build from the checkout. Each command below exists in this tree.

1. `scripts/install.sh --prefix <absolute dir>` installs into a directory you made (it builds in release mode,
   which takes minutes; `README.md`, "Try it").
2. `runbook check` checks the runbooks and their bindings; a program binding with a `*` row and no `timeout` row is
   the case the breaking change above is about.
3. Check the release: `task release:check VERSION=0.11.0`, and the experiment records with
   `sdc-experiment check --all`.

### Limits

- **No binary asset.** A user builds from a checkout with `scripts/install.sh --prefix <dir>`; the script is the
  source of an asset that does not exist yet (`docs/releasing.md`, "The binary").
- **The install script builds on the machine it runs on and installs from the checkout it lies in.** It copies
  only files git tracks and refuses a checkout whose git cannot be asked. Two installs at once into one prefix are
  not held apart; an install from an archive lacks the links and dot files of a git checkout; a release install
  after a branch was moved from another work tree is refused until an input of the build changes; a checkout with
  the reftable format cannot be installed. `scripts/install.sh --help` has each.
- **No evaluation run was made on this code.** The records of `experiments/` ran on earlier code; this release
  claims no measured change over 0.10.0. The fifth Loom evaluation record, `parity-loom-strong-5`, is registered
  and planned: it has no run yet.
- **The rework allowance is not observed in a full run.** The cycle entries that show it, `decider-rework-spent`,
  `rework-fresh-allowance` and `implement-percause`, stay `pending` (`docs/cycles-suite.md`); no run has told a
  `rework_limit` of 2 from 3.
- **The bindings check follows Loom's decoder for the forms it names.** Five forms (`merge_budget_limit`,
  `merge_budget_zero`, `merge_budget_unrelated`, `merge_in_action`, `complex_key`) were measured to be refused by
  Loom when they were measured, at `d8944d49`; no measurement of them at `ed644a4d` is recorded, no other form is
  claimed refused as Loom refuses it, and the 1 MiB text bound of Loom's reader is not checked (`CHANGELOG.md`).
- **The slow lane `task test:loom-in-process` compares a library of `ed644a4d` with the child binary of Loom
  `70b0e6e0`** (its sha256 is pinned in `runbook/tests/loom_run/slow.rs`); no `b10x-loom` of `ed644a4d` was built for
  it (`docs/loom-run.md`).
- **The recorded cycles run in `docs/cycles-suite.md` is at Loom `d8944d49`.** This preparation did not run
  `task test:cycles-loom`; the file's last record of the whole suite is 55 cycles, `40 of 40 as expected, 15 pending`.
- **Only `runbook run` writes `runner.json`** (`runbook/src/loom_run/run_loop.rs`). A run of the daemon's stub
  runtime, in which nothing is executed, and a run directory an older `runbook` wrote have none, and the inspector
  shows them as it showed them before.
- **The line of the step in flight is not shown.** Loom pipes a bound program's output into its own process and
  returns the last bytes when the program ends; the only file that grows while a step runs is under
  `work/.sdc/llm/`, a dot-directory the inspector never serves (`docs/loom-run-directory.md`).
- **`runner.json` and the start lines are what files of the run directory claim.** Under `--confinement local` a
  bound program can write the run directory, so the inspector's answer is a reading of those files, shown as text,
  and nothing decides on it.
- **A run with no money cap named is not limited in money.** `runbook run` and `sdc-experiment` start a run with
  no `--cap-micro-usd` and no `--max-llm-calls`; the daemon with `--runtime loom` is the exception, it requires its
  caps and their ceilings (`docs/loom-run.md`, `docs/daemon-api.md`). A call of unknown cost in a run that names no
  spend cap books nothing. In a run opened with a model node the printed command of a handoff runs as printed under
  a named cap too, so several steps spend from one reservation before the cap is looked at again; the story
  `handoff-under-a-named-cap-runs-one-step-at-a-time` (proposed) is the bound for it.
- **A daemon run is read on disk.** Its products are under the daemon's state directory (`runs/<run_id>/` and
  `workspaces/<run_id>/`, `docs/daemon-api.md`): no tool or route serves them yet, and served by the daemon the
  Products tab says "the daemon serves no files of a run yet".
- **The daemon runs a stub unless asked.** `runbook serve` runs the stub runtime, in which nothing is executed,
  unless `--runtime loom` is given (`docs/engine.md`).
- **The cycles that run `change.review` and the request entries are not observed as `expected` here.**
  `docs/cycles-suite.md` says that no entry changed from expected to another state is not observed on the host
  where they were run; it needs one run of the suite at a load where a cycle ends inside Loom's 60 s bound, and
  that run has not been made.
- **No statement about speed, quality or cost goes beyond `experiments/`.** A figure in these notes is a count
  read from the tree or from a command named above. The times in `CHANGELOG.md` were measured on the build host or the
  forge and are in no record of `experiments/`.
- **The inspector is read-only and has no route to the daemon** (`ui/README.md`).
- **`--confinement local` is unconfined** (`docs/loom-run.md`): a bound program can write the whole run directory.
- `task check:ess-suite:slow`, the slow lane `task test:cycles-loom`, `task test:install` and `task docs:test` were
  not run for this release.
