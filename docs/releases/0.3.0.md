# Runbook 0.3.0

The first minor release after the naming of Runbook. The bindings now run under Loom's program
contract as well as under the driver, the model's instructions are files, Canon 0.10.0 is pinned,
and four changes to what a run does are merged behind switches that are off by default. The
`runbook` command, the `runbook` plugin and the run inspector's view file are new, the bug-fix
runbook takes a ticket and a repository in any language, and the local gate now equals the forge.
A source release at tag `0.3.0`; nothing is published to crates.io and no interface is stable.
`CHANGELOG.md` lists the changes with their commits. Read `docs/releases/0.2.1.md` for the release
this one follows.

### What changed for a user

- **Tools under Loom's program contract.** The tools the bindings run moved from
  `driver/examples/sdc/tools/` to `bindings/tools/` (`sdc-tool.sh`, `llm-node.sh`, `decider.sh`,
  the four LLM adapters, `node-classes.json`, `consistency-rules.json`). With `LOOM_CASE` set they
  run under Loom's program contract (arguments on standard input, `LOOM_RETRY_FEEDBACK`, the
  binding's values as argv, the driver's binaries from `PATH`); without it they run as before,
  under the driver. In Loom mode the epic and the story of a case come from
  `LOOM_PARENT_CASE_NAME` and `LOOM_CASE_NAME`. `docs/loom-bindings.md`, "Tool changes".
- **Bindings in Loom's format.** `bindings/*.yaml`: the nine bindings files in `loom.bindings/1`,
  66 bindings, beside the JSON files the driver still runs from. `bindings/PENDING.md` lists what
  the format cannot express yet. The driver does not run the YAML files; `scripts/check-bindings.sh`
  checks them against the JSON files and the protocols. Each tool path is `tools/<file>` with no
  `..`.
- **Instructions are files.** What a model call is told is in `instructions/`
  (`<action>.md`, `shared/`, `decider/`, `{{name}}` placeholders), named by `llm.instructions` in
  each binding for the 14 agent actions and the decider. `llm-node.sh` and `decider.sh` read and
  fill them. `driver/tests/bugfix_prompt.rs` holds 40 golden prompts (`instructions/golden/`, 26 of
  the nodes and 14 of the decider) byte for byte. The two programs refuse an instruction path that
  is not `instructions/<...>.md` or has a `..` segment (exit 126).
- **Canon 0.10.0.** `driver/canon-pin.json` pins Canon 0.10.0. Every script resolves one binary
  (`CANON`, else the cached pinned install) and refuses another `canon --version`; no script builds
  or enters a Canon checkout. `runbook doctor` compares the version with the pin. The 52
  `cases/*/decision.json` are regenerated; no claim, action or outcome changed.
- **ess 0.96.0 in the tools.** `sdc-tool.sh` runs ess 0.96.0 whatever `ess` is on `PATH`, so a
  conformance line in a story's test log no longer depends on the installed ess.
- **The finding cycles as data.** `cycles/suite.yaml` (`runbook.cycles/1`) lists the 127 cycles of
  `scripts/run-finding-cycles.sh`, 125 expected and 2 pending, and `task check:cycles-suite` holds
  it equal to the script. `docs/cycles-suite.md`.
- **The run inspector reads a view file.** `views/sdc.view.json` (`runbook.view/1`) holds the
  phases, file kinds and tool owners; `--view FILE` and `--no-view`. A runbook that is not SDC can
  ship its own. `ui/README.md`.
- **The `runbook` command.** `runbook doctor` checks the assets, the Canon binary and the programs a
  run needs, one line per check with what to do on a fail; `runbook list` lists the runbooks and
  child protocols; `runbook --version`. `run`, `ui` and the other commands are not built.
- **The `runbook` plugin.** `plugin/` and `.claude-plugin/marketplace.json`: the skills
  `workflow-builder`, `harden` and `record`, for Claude Code and Codex. Its manifests carry the
  repository version.
- **The bug-fix runbook** starts from a ticket document (`sdc.ticket/1`) on a clean git worktree
  (`sdc-bugfix seed --ticket`, `scripts/run-trial.sh --bugfix-ticket`) and works on a repository of
  any language: its commands are the case's `checks.yaml` (`sdc.checks/1`). Tested: Rust,
  JavaScript with `node --test`, and a supplied `checks.yaml`; the Go, Python, Java, npm and make
  rows of `checks-detect.yaml` are not tested.
- **Local gate equals the forge.** `rust-toolchain.toml` pins rustc 1.99.1 for the local gate and
  CI, `.cargo/config.toml` drops debug info from the dev and test profiles, and
  `task ci:watch SHA=<commit>` exits non-zero unless every forge run of a commit succeeded.
- **Planning-only pull requests skip the tests.** A change of only planning or prose files passes
  `Documentation validation` without building or testing and deploys nothing; a docs-site change
  skips the `sdc-protocol-site` unit tests.
- **The docs test step is within budget.** `task docs:test` runs with four workers, 60 s per test,
  120 s for the step, and prints the ten slowest tests; on the release tree it ran 54 tests in 49.7 s, the slowest 10.0 s.

### Changes behind switches, off by default

A change in what a run does merges off by default until its experiment record holds
(`docs/improving.md`, "Run switches"). None of the four has been measured: the records are
registered and have no run.

| Switch | Default | On |
|---|---|---|
| `SDC_IMPLEMENT_MODE` | `session` | `change.implement` is one request with its whole input assembled by a program (`request`) |
| `SDC_RULE_APPROVALS` | `off` | under A5, context, roadmap and release approvals are taken by `rule:autopilot` when the program check guarding each passed at the exact revision |
| `SDC_REVIEW_MODE` | `session` | `change.review` is one request, with no tools, on one document of facts (`facts`) |
| `SDC_IMPLEMENT_COVERAGE` | `off` | `change.implement` cites each requirement; `sdc-reply check-coverage` refuses the revision before `tests.run` when one is missing |

The cycles `rule-approvals-default`, `review-mode-default` and `implement-coverage-default`
re-drive the committed stub recording with every switch unset.

### Limits

- Every limit of 0.2.1 stands: three runs per setting and tree; the story's `tests.run` repeats the
  interpreted suite; the conformance observation is off by default; the binaries, environment names
  and protocol ids still say `sdc`; the driver's runtime parts are a temporary copy of what the
  Loom runtime must provide.
- The YAML bindings are not run by anything yet; the driver runs the JSON files.
- `runbook --version` prints 0.1.4: the `runbook` crate is not among the files of the release
  version.
- The Go, Python, Java, npm and make rows of the bug-fix runbook's marker-file table are not tested.
- No experiment has tested the four switches.
