# Runbook 0.4.0

A minor release of 0.3.1, the same day. It adds two things that run: the Runbook daemon (`runbook
serve`) on a stub runtime, and `runbook loom-run`, which runs one case on a pinned `b10x-loom` binary.
A source release at tag `0.4.0`; nothing is published to crates.io and no interface is stable.
`CHANGELOG.md` lists the changes with their sources. Read `docs/releases/0.3.1.md` for the release this
one follows.

### What this release holds

- **The daemon (`runbook serve`).** One process for many runs, with a bearer token, behind
  `--principal person:<id>|agent:<id>` (required, fixed for the life of the process).
  - The API is the one specified in ESS (`ess/domains/daemon.yaml`): 5 commands and 12 views over
    HTTP and JSON (`ess/generated/openapi/openapi/runbookd.yaml`, `docs/daemon-api.md`). The 12
    scenarios of `ess/scenarios/daemon-*.yaml` pass against the running daemon and on the
    interpreted target (`story:daemon-api-specified-in-ess`,
    `story:daemon-synthesized-suite-has-no-refusal`).
  - The three event views answer as a server-sent event stream with resume by position. A journal
    survives a restart, and a run that was live when the daemon stopped ends `orphaned`
    (`docs/daemon-api.md`, "Event streams").
  - MCP: `runbook mcp` (standard input and output, as a client of a running daemon) and
    `runbook serve --mcp` (streamable HTTP at `/mcp`, behind the token check) expose 7 tools:
    `submit_run`, `list_runs`, `read_run`, `read_events`, `read_open_decisions`,
    `answer_decision`, `cancel_run` (`docs/mcp.md`, `runbook/src/mcp/tools.rs`).
  - `runbook serve --ui` serves a page compiled into the binary, with a Decisions drawer that lists
    the open decisions of the selected run and answers one (`docs/daemon-api.md`, "The web UI").
  - The guard refuses a `Host` that is not the listen address on a loopback listener, an `Origin`
    that is not the request's own host (`403`), and a command that is not JSON (`415`); a token
    shorter than 32 bytes is refused at start.
  - The CLI is a client of the daemon: `runbook run --detach`, `runbook runs
    list|show|events|cancel|decisions` and `runbook decide` (`docs/cli.md`). `runbook run` without
    `--detach` exits 64.
- **`runbook loom-run`.** One case tree through the `b10x-loom` binary as a child process
  (`docs/loom-run.md`).
  - The binary's sha256 is checked, `--confinement` has no default, a spend ledger under a file lock,
    a model-call cap and a wall-time cap bound the run, and the login link lives in a private
    directory for the length of the run. It is pinned to Loom `5af3f9c2`.
  - The decider's answers come from `bindings/tools/answers.yaml` through the helper `sdc-answers`,
    so a model run can pass `scope.answer` (`docs/loom-run-decisions.md`).
  - `sdc-experiment` knows `runner: loom` (`docs/workflow-metrics.md` § 7.1), and `sdc-experiment
    run <record> --login-file <path>` names the login for one launch.
  - `runbook parity summarize --loom-run <dir>` reads the run directory of `loom-run`. The stub
    cycle through `runbook loom-run` on `5af3f9c2` (`--confinement local`, scripted approvals, no
    model) compares `parity: identical` with the driver's (`docs/parity.md`, "Identical comparison on
    Loom `5af3f9c2`").
- **Records.** `experiments/parity-loom-strong.yaml` (abandoned: its three runs ended before any model
  call, the adapter found no login under Loom) and `experiments/parity-loom-strong-2.yaml` (complete,
  below); `approval-record:release-0-3-1` and `experiments/release-0.3.1.yaml`, the registration of
  the nine runs of 0.3.1.

`runbook --version` prints 0.4.0.

### How to try it

The binaries are built with `cargo build --bins` in `driver/` and `runbook/`. Every command below
was run with `--help` on this tree.

1. Start the daemon on its stub runtime: `runbook serve --principal person:<id> --ui` (options:
   `--listen`, `--state-dir`, `--token-file`, `--mcp`). It prints `runbook: listening on
   http://127.0.0.1:<port>` and says on standard error that the runtime is a stub
   (`docs/daemon-api.md`, "Running the daemon").
2. Submit a run to it: `runbook run --detach --intake <file> --daemon http://127.0.0.1:<port>
   stub-decision`. The preset `stub-decision` raises two decision requests and waits.
3. Read and answer: `runbook runs list`, `runbook runs show <run>`, `runbook runs events <run>`,
   `runbook decide <run> <request> A` (or answer in the page's Decisions drawer).
4. Compare a loom-run directory with a driver run: `runbook parity summarize --loom-run <run dir>
   --output <file>`, then `runbook parity compare` on the two summaries.

`runbook loom-run` needs the Loom binary; see Limits.

### The runs of `parity-loom-strong-2`

The three runs of the record (the to-do idea, strong setting, through Loom `5af3f9c2`, tree
`ee6b50bd455a`) each made three model calls in `IDEA-1.intake` (`idea.dissect`, `questions.write`,
`questions.answer`) and ended `stopped: decider_cannot_decide`: the action `scope.answer` is a question
in the driver, and the runner had no answers file yet. Spend: 0.136, 0.116 and 0.114 USD; wall 59, 48
and 46 s; furthest stage `intake` (`experiments/parity-loom-strong-2/report.md`). The three driver
runs of the strong setting of `release-0.1.2` answered `scope.answer` 5, 2 and 4 times. The
commit that closed the record (`dbd81a255`) says no comparison with the tolerance of
`story:parity-run-on-loom` is possible from these runs.

### Limits

- The daemon runs cases on its stub runtime only; the engine that runs a case on Loom inside the daemon is not in this release.
- `runbook loom-run` needs a `b10x-loom` binary built from a Loom commit that is not published.
- No parity verdict between the driver and Loom exists: the three runs of `parity-loom-strong-2` stopped at `scope.answer` before the answers file existed (0.136, 0.116 and 0.114 USD, 59, 48 and 46 s, furthest stage `intake`).
- The driver and its scripts are still the default runner of every experiment record.
- The full set of finding cycles was not run on this tree; the last full runs were on `8bddf508` and `b44f99b9b` (126 of 127 expected cycles as expected, `pool-wait` failed; fixed in `4133330ac`, not run again in full; `docs/releases/0.3.1.md`, "Checks").
- The nine runs of `experiments/release-0.3.1.yaml` are running and have no result yet.
- Every limit of 0.3.1 that this note does not change stands, among them that under Loom the exits 69 and 70 are recorded as `failed` and that the comparison of the stub cycle covers no run with a model.
