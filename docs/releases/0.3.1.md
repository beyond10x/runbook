# Runbook 0.3.1

A patch release of 0.3.0, the same day. Its reason is one defect: a step that waited for the shared
build pool was recorded as a failed test run, which stopped the registration runs of 0.3.0 (below).
It is not a one-change release. It also carries the rest of what merged after the 0.3.0 tag, and the
groups are listed under "What this release holds". A source release at tag `0.3.1`; nothing is
published to crates.io and no interface is stable. `CHANGELOG.md` lists the changes with their
commits. Read `docs/releases/0.3.0.md` for the release this one follows.

### What this release holds

This release carries more than one change. Six groups, each item with its story or commit:

- **The pool wait is not a failed run (the reason for the release).**
  - The story tool: `sdc-tool.sh` bounds the wait for a build slot (`--pool-wait`, one bound per
    step), cancels a job still queued and exits 69 without running the command; a job the pool ends
    at its run limit exits 70. The driver runs a step with exit 69 up to 3 times, records nothing
    and ends `pool_wait_spent` (exit 5); exit 70 ends the run at once with `run_over_time`.
    `sdc-run-metrics` counts `pool_waits` and `ran_over_time` apart from failures
    (`story:pool-wait-is-not-a-failure`, `5a4ba7fb`, `c3dc6282`).
  - The bug-fix tool: `sdc-bugfix` does the same for `repro.run`, `tests.run` and `gate.run`
    (limits 3000, 3000 and 4200 s); two finding cycles, `bugfix-pool-wait` and `bugfix-over-time`,
    drive it to both exits (`8bddf508`, `ff576283`, `27c64319`).
- **`runbook check` and the `--only` option of the cycles.** `runbook check` reads a checkout's text
  layout and prints one finding per line (`story:runbook-check-of-the-text-layout`, `f7954626`).
  `scripts/run-finding-cycles.sh <dir> --only <names>` runs named cycles
  (`story:finding-cycles-run-by-name`, `f2429629`, `0de97523`).
- **The driver's test budget.** One integration-test binary (`driver/tests/main.rs`), a test over
  60 s is killed, the step fails over 120 s (`task test:driver`; `story:driver-test-budget`,
  `357f218c`). The UI test step has the same budget and runs beside the driver's in `task check`
  (`story:ui-test-step-budget`, `5cbed3f5`, `8d619e2c`), and `scripts/check-protocols.sh` compares
  digests with a committed ledger and ends in under a minute (`story:check-protocols-budget`,
  `fc6d565a`).
- **Instruction files for prompts and tool texts.** The model prompts of `sdc-reply implement-run`
  (request mode), `sdc-conform` and `sdc-unstick`, and the texts of `in/feedback.md` and the
  requester request, are files under `instructions/`, held byte for byte by goldens
  (`story:rust-prompts-as-instruction-files`, `77550bac`; `story:tool-texts-and-paths`, `2dc0f484`).
  The bindings name the registrations of their protocol files and state `program_root`
  (`story:bindings-name-real-registrations`, `f9b38d67`).
- **`runbook parity` and the first equal comparison.** `runbook parity summarize|compare|approvals`
  reads a driver run and a Loom `tree status` into one summary and compares them by a table of
  rules (`story:parity-run-on-loom`, `7eb1a52d`, `1b811109`). The first comparison of the stub cycle
  under the old driver and under Loom `2c0a6f48` is equal on what both sides record: 8 cases, 69
  evidence records, 54 program runs, 5 person steps, 62 product files. Six members that Loom's
  status holds nothing for are named, not compared. It covers no run with a model
  (`story:parity-first-run`, `31866d7c`, `docs/parity.md`, "First equal comparison").
- **The daemon's ESS specification and plan, without the daemon.** In this tree: the ESS domain
  `sdc.daemon` (`ess/domains/daemon.yaml`), 10 scenarios (`ess/scenarios/daemon-*.yaml`), the
  generated JSON Schemas and the OpenAPI document `ess/generated/openapi/openapi/runbookd.yaml`,
  `task check:ess-generated` (in `task check`) and `docs/daemon-api.md`
  (`story:daemon-api-specified-in-ess`, `42cb7bad`); the epic `epic:runbook-one-binary-and-daemon`
  with its stories, `docs/library-entries.md` and the section "Where Runbook is going" of
  `AGENTS.md` (`f915fb49`). Not in this tree: `runbook serve` and `runbookd`, any handler of the
  API, the event stream, MCP and the embedded UI. The `runbook` command has `doctor`, `list`,
  `check`, `parity` and `--version`; the daemon work on branches outside this release is not part of
  it.

Smaller changes, all in `CHANGELOG.md`: the run inspector reads parsers and decisions from its view
file (`story:ui-view-data-parsers-and-actions`, `8642808c`) and keeps one view per request
(`96b198aa`); the bug-fix cycles assert the red-then-green evidence
(`story:red-then-green-as-evidence`, `fbd84489`); `runbook parity` errors name the file they could
not read. `runbook --version` prints 0.3.1.

### The registration runs of 0.3.0 were stopped

The 9 registration runs of release 0.3.0 (record `release-0.3.0`, three settings, n = 3) were
stopped on 2026-11-22 after 8 had started; one had not started, and two Haiku runs had ended before
with `writer_spent`. They cost 7.90 USD in all. The record `release-0.3.0` has status `abandoned`
and keeps the run names, a `stopped` block and the 8 run summaries; its report lists the runs as
stopped.

Why: in run `release-0.3.0.strong.1` the test step waited in the shared build pool queue, was killed
at its limit of 1800 s and was recorded as a `timeout` of `tests.run`; the tree then made a new model
call to repair tests that had not run. Four more runs were in the same step. The runs therefore
measured the build queue and say nothing about the release. The fix is the first group above and is
not in tag `0.3.0`. Tag `0.3.0` therefore has no registration numbers; the runs are repeated on
0.3.1 under a record of its own, which is added after the tag and is not in this tree. A run that
ends `pool_wait_spent` is reported apart and repeated, not counted as a failure of the release.

### Limits

- Under Loom the two new exits, 69 and 70, are still recorded as `failed`: the loader has no
  `exits` member yet, and Loom does not run the step again (`bindings/PENDING.md`).
- The run inspector and `runbook parity` do not know the verdicts `pool_wait_spent` and
  `run_over_time`: the inspector shows such a run without a name for its end, and `parity` does not
  list them among the stops it compares.
- The registration numbers of 0.3.1 are not in this note: the runs are made on the tag commit.
  No run has used the 0.3.1 tree.
- The daemon is specified and planned, and not built.
- The comparison of the stub cycle under both runtimes covers no run with a model.
- Every limit of 0.3.0 that this note does not change stands: the driver runs the JSON bindings and
  Loom reads the YAML files only in the comparison; the Go, Python, Java, npm and make rows of the
  bug-fix runbook's marker-file table are not tested; no experiment has tested the four switches.
